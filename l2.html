01 Why STP is the problem
Spanning Tree Protocol (STP)

STP prevents Layer 2 loops by blocking all redundant links — only one active path is kept between any two switches. Every blocked link is wasted capacity.

In a data center, you build many parallel links for redundancy and throughput. STP throws most of them away by design.

The entire rest of this topic is techniques that either fool STP into thinking fewer links exist, or replace STP entirely so all links can forward traffic simultaneously.
02 Link Aggregation — EtherChannel
IEEE 802.3ad (2000) — fooling STP with one logical link

Bundle multiple physical cables between two switches into a single PortChannel (logical interface). STP sees only one link — nothing to block. Traffic is load-balanced across all physical cables inside the bundle.

4 physical cables
→
STP sees: 1 PortChannel
→
all 4 carry traffic
Requirements for the bundle
  • All cables must have identical speed, duplex, and native VLAN config.
  • The bundle must not flood unknown unicast back into itself.
Servers do the same thing with NIC Teaming — bundle multiple NICs into one logical interface. Both Windows and Linux support this natively via 802.3ad.
03 Cross-Switch PortChannels
Bundle links across different physical switches

Normal EtherChannel requires both ends of the bundle to connect to one switch. Cross-switch PortChannels let you aggregate links that connect to different physical switches — STP still sees one logical link.

StackWise — Cisco Catalyst 3750

  • Physically stack multiple switches together via a ring cable.
  • They share one switch identity — STP, spanning tree, VLANs all unified.
  • Up to 64 Gbps on the stack ring.
  • If a member fails, its ports drop from the EtherChannel; remaining ports continue.
  • New member added → receives running config from stack master automatically.

vPC — Nexus switches

  • Two separate Nexus switches act as one logical switch for link aggregation purposes.
  • A dedicated peer-link syncs control-plane state between the two.
  • STP sees one logical device; downstream switch sees one PortChannel.
  • Traffic load-balances across both switches.
  • Constraint: topology must be pairs of devices (can't do arbitrary mesh).
04 Layer 2 Multipathing (L2MP)
Going further — routing-like behavior at Layer 2

vPC is still limited to pairs of devices. L2MP takes the Layer 3 routing idea — ECMP, flexible topologies, traffic control — and applies it to Layer 2 switching, while still handling Ethernet unicast, multicast, and broadcast transparently.

Two implementations:

TRILL — IEEE standard (2009) Cisco FabricPath — proprietary
05 TRILL — Transparent Interconnection of Lots of Links
IS-IS routing at Layer 2

TRILL uses the IS-IS link-state routing protocol — but to route Layer 2 frames, not IP packets. Every switch (called an RBridge — Routing Bridge) learns the full network topology and computes shortest paths to every other RBridge. All links active, ECMP works natively.

Think of it as giving Layer 2 switches a router brain — without needing IP addresses on anything.
How a frame travels through TRILL
Host sends normal Ethernet frame
→
Ingress RBridge adds TRILL header
→
Transit hops decrement TTL
→
Egress RBridge strips header
→
Delivers original frame to host
TRILL header fields — know what each does
  • Hop Count (6-bit) — decremented at every switch; drops frame when it hits zero. Prevents loops.
  • Egress Nickname (16-bit) — ID of the destination RBridge (where frame exits the fabric).
  • Ingress Nickname (16-bit) — ID of the source RBridge (where frame entered the fabric).
  • M bit — set for multi-destination frames (broadcast / multicast).
  • Op-Lng (5-bit) — options length field.
  • V (2-bit) — TRILL version.
Host location learning

IS-IS handles switch-to-switch routing. A separate protocol still floods which hosts are attached to each RBridge — this information can be flooded through the fabric.

06 Cisco FabricPath
Cisco's proprietary L2MP — similar logic to TRILL, not interoperable

Supported only on Nexus 7K (F1/F3 linecards) and Nexus 5500. Uses IS-IS as its control plane. Frames are encapsulated with a FabricPath header — not Ethernet.

Leaf switch

Connects Classical Ethernet (CE) hosts to the FabricPath fabric. Has both CE edge ports and FabricPath core ports. Must be STP root for its CE domain (use priority 4096). If it's not root, ports go Root Inconsistent via RootGuard.

Spine switch

Pure backbone — all ports are FabricPath mode. No STP, no classical Ethernet. Routes frames between leaf switches using Switch IDs. Multiple spines provide ECMP paths.

Forwarding walkthrough (step by step)
Frame arrives at leaf S100 on CE port
→
MAC table lookup: dest MAC → Switch ID 200
→
Add FabricPath header
→
FabricPath table: SID 200 → interfaces e1/1–e1/16 (load balance)
→
S200 strips FP header, delivers to host
FabricPath header — key fields
  • Switch ID (12-bit) — unique per switch; used for forwarding. Populates both MAC table and FabricPath table on leaf switches.
  • Subswitch ID (3-bit) — identifies a group of hosts/devices within a switch.
  • LID (6-bit) — Local ID; identifies the specific destination/source interface.
  • Ethertype 0x8903 — marks all FabricPath frames.
  • TTL (6-bit) — decremented at each hop; prevents loops.
  • FTag (10-bit) — Forwarding Tag; identifies the spanning tree used for multicast/broadcast distribution.
  • U/L bit — set on all unicast frames; MAC addresses are locally significant.
  • I/G bit — individual (unicast) vs group (multicast/broadcast) frame.
MAC learning — "conversational"
  • Local MACs learned normally on CE ports.
  • Remote MACs (from other edge switches) are only learned if the destination MAC in the received frame is already in the local MAC table. This prevents flooding remote MACs unnecessarily.
  • Broadcast frames from the FabricPath network do not populate the MAC table.
Control plane

IS-IS runs in the FabricPath core. Goal: compute Shortest Path Trees (SPTs) between all FabricPath nodes. IS-IS is not used for MAC address advertisement — only for switch-level topology. Advantages of IS-IS: doesn't need IP (uses own L3 transport), natively supports ECMP → Layer 2 load balancing without STP, Port Channels, or vPC.

STP interaction rules
  • FabricPath leaf switches must be STP root for their Classical Ethernet domain.
  • All leaf switches should share the same (lowest) STP priority — e.g. 4096.
  • If a leaf is not root, RootGuard puts those ports into Root Inconsistent state.
07 Other routing options

OSPF over IP

  • Layer 3 link-state protocol — same advantages as TRILL (ECMP, flexible topology, traffic control).
  • Well-established and widely understood — no new protocol to learn.
  • Needs IP addresses and subnet config on every link — more overhead.
  • Broadcast traffic scales with topology size — can get noisy in large DCs.

BGP (large-scale DCs)

  • Divide groups of switches and servers into Autonomous Systems (ASes).
  • Use BGP between ASes.
  • Highly scalable — used by hyperscalers (Facebook, Google) in their data centers.
  • More complex config than OSPF but handles massive scale.
08 Multipath Routing & ECMP
Equal Cost Multi Path — using all available paths

When multiple routes to the same destination have equal cost, ECMP distributes traffic across all of them simultaneously. Provides both load balancing and fault tolerance.

Hash-based load balancing

Hash selected header fields (typically src IP + dst IP + src port + dst port) to produce a number → number selects which path this flow takes. All packets in the same flow always take the same path, preserving order.

Decisions are made locally — if a link fails, an upstream switch may still forward onto it until it learns of the failure. TCP handles recovery from dropped packets.
09 Congestion Control — the problem
Why standard TCP struggles in data centers
  • Too aggressive: Standard TCP halves its window on any packet loss (multiplicative decrease). In a DC with tiny RTTs, this is a huge overreaction.
  • False congestion signals: Switch buffers create queuing delay → inflated RTT → TCP thinks there's more congestion than there actually is.
  • TCP Incast: A client queries many servers simultaneously; they all respond at the same time → switch port overloaded → buffer overflow → mass packet loss → all TCP connections back off and retransmit together → throughput collapses drastically.
The buffer tradeoff
Larger buffers → absorb bursts → higher throughput
Larger buffers → longer queuing delay → higher latency

You cannot have both. This tension motivates DCTCP.

10 DCTCP — Data Center TCP
React to congestion early and proportionally using ECN

Instead of waiting for packet loss, use ECN (Explicit Congestion Notification) to signal congestion early — before the buffer is full.

How it works
Buffer occupancy exceeds threshold K
→
Switch marks packets with CE (Congestion Experienced) bit
→
Receiver reflects marks in ACKs
→
Sender reduces window proportionally to fraction of marked ACKs

Example: if 33% of ACKs are marked → reduce rate by ~33% (not the standard 50%). Gentler, more precise, keeps buffers small and latency low.

Limitations of DCTCP
  • Not TCP-friendly: mixed with standard TCP, DCTCP loses bandwidth — they don't play well together.
  • Still uses slow-start: the slow-start problem from regular TCP is not solved.
  • No flow prioritization: DCTCP treats all flows equally — latency-sensitive short flows aren't prioritized over long bulk transfers.
