Section 1

Sending Output Safely

Minimize Feedback to Untrusted Users

  • Say "Login failed" — never say why (bad password vs bad username).
  • Log failures server-side instead of revealing info to attacker.
  • If usernames are already public, hiding them is less important — focus on not leaking passwords.
  • Never echo passwords on screen — prevents shoulder surfing.

Don't Send Comments to Users

  • HTML/CSS/XML comments can accidentally contain passwords, session IDs, or PII.
  • Strip comments before sending to users, or keep them in a separate server-side file.

Handle Unresponsive / Full Output

  • If a browser hangs or is slow, do not let your server hang too — that's a DoS vector.
  • Release locks before replying, not after.
  • Use write timeouts on network output (measure from start of attempt).

Control Character Encoding

  • Always declare encoding explicitly — never let the browser guess.
  • If browser guesses wrong, an attacker may exploit that to inject content.
<meta http-equiv="Content-Type" content="text/html; charset=ISO-8859-1">

Content-Type: text/html; charset=ISO-8859-1

Escape Metacharacters in Output

  • Common HTML/XML metacharacters: < > & " '
  • Use an allowlist, not a denylist.
  • Escape exactly once — double-escaping or missed escaping both cause problems.
  • Many web frameworks auto-escape by default — know when they do and don't.
Tip: Prefer frameworks that escape HTML output automatically. Know the cases where auto-escaping is disabled (e.g., "raw" output helpers) — those are where bugs live.

HTTP / HTTPS / HTML Basics

Standard HTTP Methods

MethodPurposeSafe?
GETRetrieve info✅ Should have NO side effects
HEADLike GET, only headers (no body)✅ Same rule as GET
POSTSubmit form / data⚠️ Has side effects
PUTStore/replace data⚠️ Has side effects
DELETEDelete a resource⚠️ Has side effects
OPTIONSGet communication options—
TRACEShow what server receives—
CONNECTReserved (tunnelling)—
Rule: GET and HEAD must NOT buy/sell things, change status, or have side effects. If a user triggered it accidentally, they "cannot be held accountable." Use POST/PUT/DELETE for state-changing actions.

HTTP/1.1 vs HTTP/2

HTTP/1.1 Text-based; each line ends with CRLF; blank line ends request. Easier to read/debug manually.
HTTP/2 Binary (faster, compact); fully multiplexed (parallel over 1 connection); header compression; translates losslessly to/from HTTP/1.1.

HTTP/1.1 Request Example (GET)

GET /index.html HTTP/1.1
Host: www.dwheeler.com
Accept-Language: en
Connection: keep-alive
Referer: https://www.dwheeler.com/misc.html
(blank line)

HTTP/1.1 Response Status Codes

  • 2xx — Success (200 = OK)
  • 4xx — Client error (404 = Not Found, 401 = Unauthorized)

POST Request Example

POST /myform.html HTTP/1.1
Host: www.example.com
Cookie: myId=dwheeler
Referer: http://www.example.com/index.html
Content-Type: application/x-www-form-urlencoded
Content-Length: 325
Connection: keep-alive
(blank line)
(encoded form data)

GET vs POST — When to Use Each

  • GET parameters go in the URL → stored in browser history, sent in Referer headers, written to logs. Never use GET for sensitive data.
  • Use POST when: doing a state-changing action, sending sensitive info, authentication is required. If using POST, forbid GET as an alternative.
Section 3

Cookies & Session Management

How Cookies Work

Set-Cookie: name=value
Set-Cookie: name2=value2; Expires=Wed, 09-Jun-2021 10:18:14 GMT
  • Browser includes cookie on every subsequent request to that domain.
  • No expiration set → cookie deleted when browser closes.
  • Browser sends only name/value back — not the attributes.

Cookie Attributes

AttributeWhat it does
DomainWhich server domain the cookie is sent to
PathWhich URL path triggers sending the cookie
Expires / Max-AgeWhen cookie expires (seconds for Max-Age)
SecureOnly send over encrypted (HTTPS) channel
HttpOnlyCookie inaccessible to JavaScript — only HTTP/HTTPS
SameSiteLax or Strict — only send with same-origin requests (CSRF defence)

Why Sessions Are Needed

HTTP is stateless — server has no memory of previous requests. Sessions use a session ID (usually in a cookie) to link requests together (shopping cart, logged-in state).

Secure Session ID Requirements

  • At least 128 bits of random data.
  • Must use a cryptographically secure PRNG (not "add 1", not roll-your-own).
  • Encrypt session IDs over untrusted channels.
  • Use an existing, tested library/framework for session management.

Always Create a NEW Session on Login

Ignoring old sessions on login prevents session fixation attacks. Always create a fresh session ID when a user authenticates, regardless of whether they already have a session.

Session Fixation Attack

Step 1 — MalloryLogs in, gets session_id=111
→
Step 2 — Mallory→AliceSends link with ?session_id=111
→
Step 3 — AliceClicks link, logs in with session_id=111
→
Step 4 — ServerReuses session_id=111, now associated with Alice
→
Step 4 — MalloryAccesses with session_id=111 → Alice's permissions!

Fix: always regenerate session ID after authentication.

Limit Session Lifetime

  • Set both an idle timeout and a maximum session lifetime.
  • Fewer valid IDs = smaller attack window if one is stolen.
/* Java Servlet — web.xml — idle timeout in minutes */
<session-config>
  <session-timeout>60</session-timeout>
</session-config>

For maximum (absolute) lifetime, use doFilter(): store creation time in session; invalidate after max lifetime.

Logout Must Destroy Server-Side Session

  • Deleting the cookie client-side is NOT enough — the old cookie could be reused.
  • Server must invalidate the session on logout.
  • Failures: Office 365, Yahoo Mail, WordPress (as of 2013).
  • Pass: Gmail, Tweetdeck, Facebook.
  • Always provide a logout button on every page.
Section 4

Cross-Site Scripting (XSS)

Core idea: Attacker injects malicious script into a trusted site. Victim's browser receives and executes it, trusting it because it came from the real server.

3 Types of XSS

1. Persistent (Stored) Attacker submits malicious data (e.g., HTML with script in a comment). Server stores it in DB. When victim loads the page, malicious code is served and runs automatically.
2. Reflected Attacker crafts a URL/form that sends malicious data to the server. Server "reflects" it straight back in the response. Victim's browser runs it, thinking it came from the trusted server.
3. DOM-Based Client is tricked into sending itself the attack via the DOM (no server round-trip needed). See: OWASP XSS Types

Countering XSS

  • Output escaping (BEST defence) — escape all untrusted data before rendering. Use framework auto-escaping. Covers all cases if done everywhere.
  • Input filtering — strip/reject metacharacters (< > & " ') on input. Often incomplete, but useful for defence-in-depth. Use HTML-sanitisation libraries to allow safe tags like <i> without allowing <script>.
  • HttpOnly on cookies — JavaScript can't read these cookies, limiting data an XSS attacker can steal. Imperfect but helpful.
  • Content Security Policy (CSP) — see next subsection.
Avoid copying data back to user where possible — if you never echo a URL, you can never echo it wrongly.

Content Security Policy (CSP)

An HTTP response header that tells the browser what sources are trusted. Browsers only execute JS/resources from those sources.

Content-Security-Policy: default-src 'self'


Content-Security-Policy: default-src 'self' *.trusted.com


Content-Security-Policy: default-src 'self'; img-src *; script-src scripts.js.com
  • Supported: Chrome 16+, Safari 6+, Firefox 4+. IE 10 has very limited support.
  • Requires moving all inline JS to separate files (else browser can't distinguish it from injected JS).
  • Can also disable eval() and inline JS.
  • Twitter and Facebook have deployed CSP.
CSP is not a silver bullet. Attackers can sometimes work around it (e.g., injecting into HTML that leaks hidden field values to evil.com via an unclosed img tag). Use output escaping as primary defence; CSP as an additional layer.
Section 5

Cross-Site Request Forgery (CSRF / XSRF)

Core idea: Attacker causes a victim's already-authenticated browser to make an unintended request to a trusted site. Browser automatically includes the session cookie, so the server thinks it's legitimate.

How It Works — Classic Example

VictimLogged into bank.com
→
Attacker (evil.com)Page contains:
<img src="http://bank.com/transfer?amount=10000&dest=evilcorp">
→
BrowserFetches that URL, auto-attaches bank.com cookie
→
Bank.comCookie valid → transfer executed!

CSRF vs XSS

XSS — fools the CLIENT
Malicious script runs in victim's browser; browser does something bad for the attacker.
CSRF — fools the SERVER
Legitimate browser makes an unintended request; server accepts it because the cookie checks out.

CSRF Defences

1. Secret Validation Token (most common, always works)

<input type="hidden" name="csrf_token" value="23a3af01b...">
  • Server embeds a random, hard-to-guess token in every form.
  • Attacker can't read it (different origin), so they can't forge a valid request.
  • Variations: session identifier, session-independent token, session-dependent token, HMAC of session ID.
  • Most modern frameworks (e.g., Rails authenticity_token) do this automatically.

2. SameSite Cookie Attribute (best long-term solution)

Set-Cookie: session=abc; SameSite=Lax
Set-Cookie: session=abc; SameSite=Strict
  • Lax: cookie sent only for top-level navigations (safe). Chrome and Firefox now default to Lax.
  • Strict: cookie only sent when request comes from the same site.

3. Check HTTP Referer / Origin Header

Referer: http://www.facebook.com/home.php
Origin: http://www.facebook.com/home.php
  • Accept only if Origin/Referer matches expected domain.
  • Must treat "no Referer" as unauthorized (attacker can suppress it).
  • Not a complete solution alone (client vulnerabilities may subvert it).
  • Note: "Referer" is a misspelling of "Referrer" in the HTTP spec.

4. Additional Measures

  • Require re-authentication for critical operations.
  • Apply CSRF countermeasures to login page too (prevent login CSRF).
  • Auto-logout after X minutes inactivity.
  • Don't allow GET requests to have side effects (only POST for state changes).

CSRF on Non-Web Targets: Home Router Example

  • 50% of home routers use default or no password.
  • Attacker's evil.com page sends request to 192.168.1.1 (router admin) — browser forwards it with any existing auth.
  • Attacker can enable remote admin, reset password, etc.

HTTP Hardening Headers

Add these headers to make attacks harder. Quick scan tool: https://securityheaders.io/

HeaderWhat it does

Section 7

Redirection & Caching

Open Redirect / Unvalidated Redirects

Don't use untrusted user input to decide where to redirect. Solutions (OWASP order):

  1. Avoid redirects/forwards entirely if possible.
  2. If used, don't use user parameters to compute the destination.
  3. If you must use a parameter, validate and authorise the value. Use a mapping (e.g., dest=1 maps to a fixed URL) rather than the raw URL.
  4. Use OWASP ESAPI to override sendRedirect() to enforce safe destinations.

Disable Caching for Sensitive Data

  • Browsers cache pages to disk — cached sensitive pages can be read later.
  • Correct approach (HTTP 1.1):
Cache-Control: no-store
Common mistake: Using non-standard/legacy cache-disabling mechanisms. A 2013 study found 70% of financial, healthcare, insurance, and utility sites did this wrong — effectively only disabling caching in IE6. Use the standard Cache-Control: no-store.
Section 8

Same-Origin Policy & Client-Server Trust

Same-Origin Policy (SOP)

  • JavaScript can only access data on another page if both share the same URI scheme + hostname + port.
  • Primary exceptions:
    • Legacy operations: img src, submitting POST forms, including scripts.
    • Windows/frames where both set document.domain to the same value.
    • postMessage() text passing.
    • WebSockets (server checks Origin header).
    • CORS (Cross-Origin Resource Sharing) — explicit server opt-in.

Server Must Not Trust the Client

Never trust client-side validation. Attacker controls the client (including JavaScript running there). All validation and authorisation must be enforced server-side. Client-side checks are only UX improvements.
  • Store important state on the server — don't let the client dictate it.
  • Any request to change data must be checked server-side first.
  • Extra caution when running JS on client or providing direct DB access.
Section 9

Vulnerability Lists & Taxonomies

CVE — Common Vulnerabilities and Exposures

  • Vulnerability: specific mistake in specific software directly usable by attacker.
  • Exposure: configuration issue or mistake giving access usable as a stepping-stone.
  • Format: CVE-YEAR-NUMBER (e.g., CVE-2013-1380 = specific Adobe Flash bug).
  • Common naming system so different organisations can cross-reference reports.
  • More info: cve.mitre.org and nvd.nist.gov

CVSS — Common Vulnerability Scoring System v2.0

Score 0–10 (10 = riskiest) to help prioritise remediation.

Base Metrics (intrinsic, always apply):

MetricOptions
Access Vector (AV)Local / Adjacent Network / Network
Access Complexity (AC)High / Medium / Low
Authentication (Au)Multiple / Single / None
Confidentiality Impact (C)None / Partial / Complete
Integrity Impact (I)None / Partial / Complete
Availability Impact (A)None / Partial / Complete

Temporal Metrics (optional, change over time): Exploitability (E), Remediation Level (RL), Report Confidence (RC).

Environmental Metrics (optional, context-specific): Collateral Damage Potential (CDP), Target Distribution (TD), Security Requirements (CR, IR, AR).

CWE — Common Weakness Enumeration

  • Weakness = a type of vulnerability (category), not a specific bug.
  • Format: CWE-NUMBER (e.g., CWE-120 = Classic Buffer Overflow).
  • Has parent/child relationships (e.g., CWE-119 is parent of CWE-125 and CWE-787).
  • More info: cwe.mitre.org

WASC Threat Classification v2.0

Attacks include: Brute Force, Buffer Overflow, XSS, CSRF, SQL Injection, Path Traversal, Session Fixation, OS Commanding, Format String, Integer Overflows, LDAP Injection, Remote File Inclusion, Routing Detour, XML Entity Expansion, and more.

Weaknesses include: App Misconfiguration, Improper Input/Output Handling, Insufficient Authentication/Authorization/Session Expiration, Information Leakage, Insecure Indexing, Insufficient Transport Layer Protection, Server Misconfiguration.

Using "Top" Lists in Assurance Cases

  • Can't prove "zero implementation mistakes" — instead, pick a "top" list and show countermeasures for each item.
  • Default recommendation: OWASP Top 10 for web apps, SANS/CWE Top 25 for everything else.
  • Best "top" list is the one most relevant to your project and environment.
  • You do NOT need to memorise CWE numbers — but you must know what a name means if it's been covered.

Coding Standards & Checklists

SEI CERT Top 10 Secure Coding Practices

#PracticeKey Point
1Validate InputAll untrusted data: CLI args, network, env vars, user files. Eliminates the vast majority of vulnerabilities.
2Heed Compiler WarningsHighest warning level; fix all warnings. Use static and dynamic analysis tools.
3Architect for SecurityDesign software to implement security policies. E.g., separate subsystems by privilege level.
4Keep It SimpleSimpler design = fewer mistakes. Complexity makes assurance harder.
5Default DenyAccess denied by default; only allow explicitly. Permission-based, not exclusion-based.
6Least PrivilegeMinimum permissions for minimum time. Reduces attacker's opportunities.
7Sanitize Data to Other SystemsSanitize before calling shells, DBs, COTS. The calling process knows the context — it is responsible.
8Defence in DepthMultiple layers: if one fails, another catches it. Combine secure coding + secure runtime.
9Quality AssuranceFuzz testing, penetration testing, source code audits, independent security reviews.
10Adopt a Secure Coding StandardUse a standard for your language/platform (e.g., SEI CERT, OWASP).

SANS SWAT Checklist (Securing Web Application Technologies)

Error Handling & Logging:

  • Display generic error messages; no unhandled exceptions; suppress framework-generated errors.
  • Log all: authentication activities, privilege changes, admin activities, access to sensitive data.
  • Do NOT log inappropriate data; store logs securely.

Data Protection:

  • Use SSL everywhere; disable HTTP access for SSL-enabled resources.
  • Use Strict-Transport-Security header.
  • Store passwords using a strong, iterative, salted hash.
  • Securely exchange encryption keys; disable weak SSL ciphers.
  • Use valid SSL certificates from a reputable CA.
  • Disable data caching via Cache-Control headers and autocomplete.
  • Limit use and storage of sensitive data.

Configuration & Operations:

  • Rigorous change management, defined security requirements, design review, code reviews, security testing, hardened infrastructure, incident handling plan, security training.

Authentication:

  • Don't hardcode credentials; strong password reset system; strong password policy.
  • Account lockout against brute force; don't disclose info in error messages.
  • Store DB credentials securely; apps/middleware run with minimal privileges.

Session Management:

  • Session IDs sufficiently random; regenerate session tokens on login.
  • Idle session timeout; absolute session timeout; destroy sessions on tampering signs.
  • Invalidate session after logout; logout button on every page.
  • Use HttpOnly and Secure cookie flags; set correct domain/path/expiration.

Input & Output Handling:

  • Contextual output encoding; prefer whitelists over blacklists.
  • Use parameterised SQL queries; CSRF tokens in forms.
  • Set encoding for your application; validate uploaded files.
  • Use nosniff header for uploaded content; validate input source.
  • Use X-Frame-Options; use CSP / X-XSS-Protection headers.

Access Control:

  • Apply access control checks consistently; principle of least privilege.
  • Don't use direct object references for access control checks.
  • Don't use unvalidated forwards or redirects.
Section 12

PHP Security Best Practices

Configuration

  • Set register_globals = Off in PHP configuration.
  • Enable all error reporting for development: <?php error_reporting(E_ALL); ?>
  • Avoid file uploads where possible; disable in php.ini: file_uploads = Off

Dangerous Functions — Be Very Careful

If an attacker can control the string passed to any of these, they can execute arbitrary code:
eval() exec() include() passthru() popen() preg_replace() with /e require() system() backtick operator ``

PHP Sanitisation Functions

FunctionWhat it does
strip_tags($str)Returns string with all HTML/PHP tags removed. You can specify allowed tags as exceptions.
htmlentities($str, ENT_QUOTES)Converts &, quotes, <, > into HTML entities (&amp;, &lt;, etc.). The ENT_QUOTES flag also escapes single quotes.
escapeshellcmd($str)Escapes characters that could be used to inject shell commands: #&;`|*?~<>^()[]{}$\, \x0A, \xFF. Single and double quotes escaped only if unpaired.

Quick Recap

Everything in One Glance

Output Safety Escape metacharacters. Declare charset. Don't send comments. Use timeouts. Minimize error detail to users.
HTTP GET = no side effects. POST for sensitive/actions. Use HTTPS. Status: 2xx=ok, 4xx=client error.
Cookies Always set: HttpOnly, Secure, SameSite. Short expiry. Invalidate on logout.
Sessions 128-bit CSPRNG ID. New session on login. Idle + absolute timeout. Destroy on logout server-side.
XSS Escape output (primary). HttpOnly cookies. CSP header. Input filter (secondary). Attacker fools CLIENT.
CSRF Secret token + SameSite cookie (best combo). Check Origin header. Re-auth for critical ops. Attacker fools SERVER.
Hardening Headers CSP, HSTS, X-Content-Type-Options: nosniff, X-Frame-Options, X-XSS-Protection.
Redirection & Caching Validate redirect destinations. Use mapping not raw URLs. Disable caching: Cache-Control: no-store.
Trust Server must NEVER trust client-side validation. Enforce everything server-side. SOP restricts JS cross-origin access.
Vuln Lists CVE = specific bug. CWE = type of bug. CVSS = severity score 0–10. Use OWASP Top 10 (web) or CWE Top 25 (general).
CERT Top 10 Practices Validate input. Default deny. Least privilege. Defence in depth. Keep simple. Sanitize outputs.
PHP register_globals=Off. Avoid eval/exec/system with untrusted input. Use strip_tags, htmlentities, escapeshellcmd.
