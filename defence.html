Part 1 — Multiple Choice Questions (10)
MCQ 1
1. A web app exposes https://example.com/profile?user_id=123. Changing the value to 124 reveals another user's private data with no extra check. Which OWASP Top 10 category does this fall under?
Correct answer: B. This is a classic Insecure Direct Object Reference (IDOR), a form of Broken Access Control — the app trusts the user-supplied ID without verifying the requester owns that resource.
MCQ 2
2. A developer stores passwords like this: base64.b64encode("admin123".encode()). What is the core problem?
Correct answer: B. Base64 is a reversible encoding scheme with no key and no cryptographic protection — anyone can decode it instantly. Passwords should be hashed with bcrypt/PBKDF2 (one-way, salted).
MCQ 3
3. Which input, submitted as a username, demonstrates a classic SQL injection authentication bypass against SELECT * FROM users WHERE username='{input}' AND password='{input}'?
Correct answer: C. ' OR '1'='1 turns the WHERE clause into an always-true condition, returning rows regardless of the password. Option B is for SSTI, D is path traversal.
MCQ 4
4. A password recovery feature asks "What is your favorite color?" as the only verification step. This is best described as:
Correct answer: B. Weak security questions are a design-level flaw — no amount of clean coding fixes the fact that "favorite color" has roughly 10 likely answers. This is Insecure Design (A04), not a coding bug.
MCQ 5
5. A pentester finds that an error page returns: MySQL error in query "SELECT * FROM users WHERE id='1'". This is an example of:
Correct answer: A. Verbose errors leaking database type, table names, and query structure are a Security Misconfiguration (A05) — production apps should show generic error pages.
MCQ 6
6. A custom template engine renders user input directly. Submitting {{7*7}} returns 49. What vulnerability class is this, and what category does it fall under?
Correct answer: B. Evaluating {{7*7}} to 49 proves the input is being parsed as a template expression — classic SSTI, which the material groups under A06 (often arising from vulnerable/misused template components).
MCQ 7
7. An admin account is protected only by a 4-digit PIN with no lockout policy. From a network security perspective, which control would most directly mitigate the resulting brute-force risk?
Correct answer: B. A 4-digit PIN has only 10,000 combinations — trivial to brute force in seconds. Rate limiting / lockout after a small number of failed attempts (e.g. 5) is the direct mitigation for A07 Authentication Failures.
MCQ 8
8. A session cookie is set to session_token=eyJyb2xlIjoidXNlciJ9. The attacker decodes it, changes the JSON to {"role":"admin"}, re-encodes it, and sends it back — gaining admin access. What is the root cause?
Correct answer: B. This is a Software & Data Integrity Failure (A08) — the role claim isn't signed/verified (e.g. with HMAC in a real JWT), so the client can freely tamper with it.
MCQ 9
9. A "URL Preview" feature on a server fetches whatever URL a user submits, including http://169.254.169.254/latest/meta-data/. This attack pattern is called:
Correct answer: B. Tricking the server into requesting internal/cloud-metadata endpoints on the attacker's behalf is SSRF (A10) — mitigated by allowlisting destinations and blocking internal IP ranges.
MCQ 10
10. Which pairing of a network security protocol with its primary purpose is CORRECT, based on the Network Defense Fundamentals material?
Correct answer: B. IPSec operates at the network layer and secures IP communications, widely used to build VPN tunnels. WPA3 secures Wi-Fi, Kerberos is an AD authentication protocol, and TLS secures transport-layer traffic (HTTPS), not password hashing.
Part 2 — Scenario Questions (5)
Scenario 1 Easy
You're testing an internal HR portal. As a regular employee, you notice the "Edit Profile" link is hidden in your UI, but you recall that admins have a page at /admin/users. Out of curiosity, you type https://hr.megacorp.local/admin/users directly into your browser while logged in as a normal employee — and it loads the full employee list with edit buttons.
What vulnerability is being demonstrated, and what is the single most important fix?
Correct answer: B. The admin page is only "hidden" in the UI — the server isn't actually checking the user's role before serving the page. This is Missing Function-Level Access Control (A01). The fix is a server-side middleware/role check on every sensitive route, never relying on hiding links client-side.
Scenario 2 Easy
During a code review of "Kamosi Personal Dictionary," you find this Java snippet: String query = "SELECT * FROM words WHERE term = '" + userInput + "'"; Statement stmt = connection.createStatement(); ResultSet rs = stmt.executeQuery(query); A teammate says "it's fine, we trim whitespace from userInput before this line."
Is the teammate's mitigation sufficient, and what should actually be done?
Correct answer: B. Trimming whitespace does nothing to stop characters like ', --, or OR 1=1 from altering query structure. The query must be rewritten using PreparedStatement with ? placeholders (bound parameters) so user input is always treated as data, never as SQL syntax — directly matching the SonarQube SQLi remediation pattern.
Scenario 3 Medium
You're doing a CTF web challenge. The app has a "Generate Report" feature where you supply a report title, and the response renders: "Report: {your_title}". You test by submitting a title of {{config}} and the page returns the full Flask app configuration object, including SECRET_KEY and a database connection string. Separately, you notice that after login, the app sets a cookie: auth=eyJ1c2VyIjoiZ3Vlc3QiLCJyb2xlIjoidXNlciJ9.signature_part You decode the first segment and get: {"user":"guest","role":"user"}
Which TWO issues are present, and what's the correct prioritized action?
Correct answer: B. The {{config}} result confirms SSTI (A06) — and worse, it leaked the SECRET_KEY, which is often used to sign tokens. If that key is now known to the attacker, they could forge a valid signature for a tampered cookie like {"user":"guest","role":"admin"} — turning an SSTI into full account takeover via A08 token forgery. Fix: never render user-controlled strings as template syntax, and treat any leaked signing key as compromised (rotate it).
Scenario 4 Hard
You're performing an internal pentest at MegaCorp. Recon on a public-facing "Invoice PDF Generator" reveals: 1. It accepts a "logo_url" parameter to fetch a company logo: /generate?logo_url=https://partner-cdn.com/logo.png 2. The generated PDF is built by a templating library, and the invoice "notes" field is inserted directly into the template string before rendering. 3. The app runs on an AWS EC2 instance. 4. Application logs (publicly accessible at /logs/app.log due to a misconfigured web server) show: 2026-06-10 09:14:02 DEBUG generate_invoice: logo_url=http://169.254.169.254/latest/meta-data/iam/security-credentials/ status=200 size=412 2026-06-10 09:14:55 DEBUG generate_invoice: notes={{self.__init__.__globals__.os.popen('id').read()}} status=200 These two log entries are from previous testers (or attackers) and both returned HTTP 200.
Identify the FULL attack chain represented here (which vulnerabilities, in what order, and the realistic worst-case impact) — and state the most critical fix to break the chain.
Correct answer: B. This scenario chains three OWASP categories from the material into one realistic attack path:

1. A09 (Logging/Monitoring failure): Debug-level logs containing full request parameters are exposed at a public, unauthenticated /logs/app.log endpoint — this is how the tester/attacker activity becomes visible at all, and how a real attacker could harvest other users' sensitive data from logs.

2. A10 (SSRF) → Cloud credential theft: logo_url=http://169.254.169.254/latest/meta-data/iam/security-credentials/ abuses the unvalidated URL-fetch feature to reach the AWS EC2 metadata service, which can return temporary IAM credentials for the instance's role — handing the attacker cloud-level access (S3 buckets, other AWS resources, etc.), far beyond just "viewing a file."

3. A06 (SSTI) → RCE: The "notes" field is rendered as a template, and the payload {{self.__init__.__globals__.os.popen('id').read()}} is a classic Jinja2/Python SSTI-to-RCE technique that walks Python's object graph to reach the os module and execute shell commands.

Prioritized fixes: (a) Allowlist logo_url to known CDN domains and explicitly block link-local/internal ranges (169.254.169.254, 127.0.0.1, 10.x, 192.168.x, 172.16-31.x) — this single fix prevents metadata-credential theft, often the highest-blast-radius issue in cloud environments; (b) never pass user-controlled strings into a template renderer — pass them as data/context variables instead; (c) restrict debug logging of full parameters and ensure /logs/ requires authentication or isn't web-served at all.
Scenario 5 Hard
You're the lead on a small org's security overhaul (similar to setting up defenses for "Nova Development Company"). The current state: - All internal services (Git server, internal wiki, dev databases) sit on a flat /24 network with no segmentation. Any compromised laptop can directly reach the database on port 3306. - Developers SSH into production servers using shared root credentials ("devteam" / "devteam123"), no MFA, no per-user accounts. - The web app's login endpoint has no rate limiting (8-character mixed-case+digit passwords are required, but brute-forcing is otherwise unrestricted). - There is no IDS/IPS, and firewall rules allow ANY -> ANY on all internal subnets. - No centralized logging; each server keeps local logs that are rotated and deleted after 24 hours. - A recent incident: an attacker phished a developer's laptop, then pivoted to the database server directly, exfiltrated customer data, and the team only discovered it 3 weeks later via a customer complaint — by which time the relevant logs were gone.
Using the CIA Triad and the Preventive/Detective/Corrective control framework, design a PRIORITIZED remediation plan. Which single first step would have most changed the outcome of the described incident, and why?
Correct answer: C. This scenario stitches together nearly the entire Network Defense Fundamentals framework into one incident post-mortem:

What failed (mapped to CIA): Confidentiality was breached (customer data exfiltrated), and the org had essentially zero visibility into Integrity/Availability impact because of weak monitoring.

Why the "ANY -> ANY" flat network matters most: The initial compromise (phished laptop) was arguably unavoidable purely through technical controls — social engineering succeeds against people. But the attacker's ability to go from "one compromised laptop" to "direct access to the production database" in one hop is a network design failure, not just an endpoint failure. Network segmentation (Preventive control — ACLs separating user/workstation subnets from database/server subnets, least-privilege firewall rules instead of ANY->ANY) would have either blocked the pivot outright or forced the attacker through additional, detectable hops.

Why centralized logging matters second: Local logs rotated/deleted after 24 hours guarantee that any slow-burn attack (3 weeks, in this case) leaves no forensic trail. A centralized logging/SIEM setup (Detective control) with longer retention and alerting on anomalies (e.g., a workstation suddenly opening a connection to port 3306 on the DB server) would have surfaced the incident in hours, not weeks — turning a "discovered by customer complaint" disaster into a contained incident.

Other items (shared credentials/no MFA on SSH, no rate limiting on login, no IDS/IPS) are all real findings worth fixing — shared root SSH access in particular is a severe finding (no accountability, can't revoke individual access, violates least privilege) — but segmentation + centralized logging directly address the root cause of how this specific incident escalated and went undetected, making them the highest-priority first steps. Password rotation policies (B) and brand of firewall (A) are largely irrelevant to what actually happened.
