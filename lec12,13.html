01

Core Concepts & Buzzwords

Source Code Review

Manually inspecting source code to find security flaws. Also called Static Code Analysis. The goal is to catch what automated scanners miss.

SAST

Static Application Security Testing — automated scanners that analyze code without running it. Examples: Veracode, Checkmarx.

SDL

Security Development Lifecycle — framework that embeds security at every phase: Architecture → Development → Deployment → Production.

Manual vs Automatic

You need both. Auto-scanner runs first during CI/CD. Manual review happens before deployment to catch what the scanner missed.

False Positive

When a scanner flags something that is NOT actually a vulnerability. You (the AppSec analyst) evaluate and approve or reject these.

Security Champion

The development team lead responsible for security. They submit false positive requests in the SAST portal and await your approval.

⚠️ Before starting a code review, always review the Threat Modeling document first — understand the project's architecture, entry points, assets, external dependencies, trust levels, and security threats.
02

Secure Development Lifecycle (SDL) Flow

1
Architecture Phase
Define architecture. Use the secure coding practices document as a reference for all technical decisions. Threat modeling happens here.
2
Development Phase (CI/CD)
Developers push code to the build server daily. SAST scanner (e.g. Veracode) automatically scans after each build and flags vulnerabilities. No HIGH or CRITICAL issues allowed before release.
3
Before Gating (Deployment)
Manual source code review + Web Intrusion testing. Scanner backlog must have zero High/Critical issues. Risk assessment done by Risk Analyst. Pentester runs final tests.
4
Production
Yearly health check: Network Infrastructure + Web Intrusion. Pentester reviews the live environment.
Tools in the SDL
  • Veracode / Checkmarx — SAST scanners
  • Sonatype / Nexus / BlackDuck — Third-party library scanners
  • Jenkins / Team Foundation Server — Build servers (CI/CD)
  • Nessus / Nexpose — Network infrastructure scanning
  • Burp Pro — Web intrusion testing
💡 When evaluating SAST scanners: check the Gartner list, scan multiple apps with each, then compare false positives vs vulnerabilities found. Don't blindly trust rankings — test yourself.
03

SAST Scanners — How They Work

Continuous Integration Flow
  • Dev finishes work → pushes to build server daily
  • SAST scanner triggers automatically on each build
  • Flags any new vulnerabilities in the code
  • AppSec analyst reviews results with dev lead (Security Champion)
  • Security Champion submits false positive requests via SAST portal
  • You approve or reject false positives
  • Before release: backlog must have zero High/Critical issues
Manual Review Happens After Automatic
  • Manual review catches what scanners miss
  • Neither alone is enough — you need both
  • Manual review occurs pre-deployment (gating stage)
  • Your role: support dev team + report scanner bugs to vendor
🔴 Scanners are NOT perfect. Many false positives arise. You are the gatekeeper for approving/rejecting them.

Authentication & Password Management

Must-Do Rules
  • Use TLS (HTTPS), never HTTP cleartext for credentials
  • Enforce authentication on ALL pages except intentional public ones
  • Auth logic must be validated server-side only
  • Hash passwords with strong algorithms — NOT MD5 or SHA-1
  • Use salting alongside hashing
  • Password hashing must happen server-side
  • Validate ALL auth data after all fields are filled (not field-by-field)
  • Use only HTTP POST for transmitting credentials
  • Re-authenticate before critical operations
  • Use Multi-Factor Authentication (MFA) for high-value accounts
  • Disable "Remember Me" for password fields
  • Report last login (success or fail) to user at next login
Error Messages & Lockout
  • Never say "Invalid username" or "Invalid password" separately
  • Always say: "Invalid username and/or password"
  • Error responses must be identical in display AND source code
  • Lock account after 5 failed attempts (common standard)
  • Lockout long enough to stop brute force, short enough to prevent DoS
  • Alert user via email or SMS on password change/reset
Password Complexity Policy
  • Minimum 8 characters (16 is better, passphrase even better)
  • At least 1 uppercase letter
  • At least 1 special character
  • At least 1 number
  • Password fields must not echo the input (use type="password")
  • Disable autocomplete on password fields
  • Prevent password reuse
  • Passwords at least 1 day old before change allowed
Password Reset Rules
  • Reset questions must have sufficiently random answers
  • "What is your favorite color?" = BAD question
  • Email resets: send only to pre-registered address
  • Include a temporary random link/password with short expiry
  • Temp passwords must be changed on next use
  • Third-party auth credentials must be encrypted — never in cleartext config files
05

Authorization & Access Control

Authorization Rules
  • Authorization must be implemented server-side
  • If app can't access security config (e.g. DB down) → deny all access
  • Authorization must exist on every web request including API endpoints
  • If auth data stored client-side → must be encrypted
  • OS/service accounts should have least privilege
  • Only allow HTTP methods: GET, POST, PUT, DELETE
  • Force logout immediately after authorization changes take effect
  • Never rely solely on the Referer header — it can be spoofed
Access Control Rules (OWASP)
  • Use a single site-wide component for all access checks
  • Access controls must fail securely
  • Restrict protected URLs, functions, files to authorized users only
  • Restrict direct object references to authorized users
  • Server-side and presentation layer access rules must match
  • Limit transactions per user/device per time period (rate limiting)
  • Disable unused accounts (no more than 30 days after expiry)
  • Enforce disabling of accounts when authorization changes (role change, leaving company)
  • Create an Access Control Policy document
06

Session Management

Session Rules
  • Sessions managed server-side only
  • Session IDs must be random (not predictable)
  • Logout must fully terminate the session
  • Logout available on all authenticated pages
  • Set inactivity timeout — calculate based on security risk of resource
  • Never put session IDs in URLs, logs, or error messages
  • Session ID lives in the Cookie header only
  • Set Secure attribute on cookies (HTTPS only)
  • Set HttpOnly attribute on cookies (blocks JS access)
Advanced Session Rules (OWASP)
  • Generate new session ID on any re-authentication
  • If session established before login → close it, create new one after login
  • Disallow concurrent logins with same user ID
  • Generate new session ID when switching HTTP → HTTPS
  • Regenerate session ID periodically (mitigates hijacking)
  • Use per-session random tokens for sensitive operations (CSRF protection)
  • Use per-request tokens for highly critical operations
  • Disallow persistent logins; enforce periodic termination
07

Cryptography

Cryptography Rules
  • All crypto logic on the server-side
  • Critical data (DB connection strings, passwords, keys) must be encrypted, never cleartext
  • Crypto keys accessible only to super admins
  • All random items (numbers, filenames, strings) use cryptographically secure random generators
  • Use latest/greatest secure algorithms
  • Reference NIST at https://csrc.nist.gov for algorithm guidance
  • Modules must be FIPS 140-2 compliant (or equivalent)
  • Crypto modules should fail securely
  • Have a key management policy
What NOT to Use
  • MD5 — weak, do not use for passwords
  • SHA-1 — weak, avoid if possible
  • Hardcoded credentials anywhere in source code
  • Cleartext passwords in config files
  • Always use salted hashes for stored passwords
  • Protect the master secret from unauthorized access
📚 NIST = National Institute of Standards and Technology. The authority on approved cryptographic algorithms.
08

Input Validation

Core Rules
  • All data validation on server-side (trusted system)
  • Encode data before validating (canonicalize first)
  • All validation failures → reject input with custom error message
  • Validate everything processed in backend: form fields, hidden fields, URLs, headers
  • Validate data type, range, and length
  • Use a whitelist of allowed characters whenever possible
  • Specify character set (e.g. UTF-8) for all input sources
  • Validate data from redirects (attacker can bypass pre-redirect validation)
  • Use a centralized input validation routine
  • Truncate all input strings to reasonable length before copy/concatenate
  • No hardcoded SQL queries in source code
Hazardous Characters to Check
< > " ' % ( ) & + \ \' \"
Also Check Discretely
  • Null bytes — %00
  • New line chars — %0d %0a \r \n
  • Dot-dot-slash — ../ ..\ (path traversal)
  • UTF-8 encoded traversal — %c0%ae%c0%ae/
  • Verify only ASCII in HTTP headers (request & response)
09

Output Encoding

Output Encoding Rules
  • All encoding logic on the server-side
  • Use a standard, tested routine for each type of outbound encoding
  • Contextually encode all data returned to client from outside the app's trust boundary
  • Encode all characters unless known safe for the intended interpreter
  • Sanitize all output for: SQL, XML, LDAP queries
  • Sanitize output for OS commands
  • HTML entity encoding is one method but doesn't work in all contexts
  • Apply output encoding based on context: HTML body, HTML attribute, JS, CSS, URL, etc.
💡
Canonicalize means reducing various encodings to a single simple form before validating. This prevents double-encoding attacks.

HTML Entity Encoding replaces characters like < with &lt; making them inert in browsers.
10

Error Handling & Logging

Error Handling Rules
  • Never disclose sensitive info in error messages (stack traces, debug info, session IDs)
  • Use custom error messages and custom error pages
  • Use generic error handlers that hide implementation details
  • App handles errors — don't rely on server configuration
  • Properly free allocated memory when errors occur
  • Error handling logic for security controls → deny access by default
  • When exceptions occur, exit the function securely
  • Error/monitor logs must NOT be on the same server (prevents DoS by filling disk)
What to Log (Always)
  • All validation failures
  • All authentication attempts (especially failures)
  • All authorization failures
  • Tampering events (e.g. URL manipulation, SQL injection attempts)
  • Invalid or expired session token usage
  • All administrative functions and security config changes
  • All cryptographic module failures
  • Backend TLS connection failures
  • Access from certain countries / high-frequency requests
  • All system exceptions
Logging Best Practices
  • Logging controls on server-side
  • Log both success and failure of security events
  • Restrict log access to authorized individuals only
  • Use a master/centralized logging routine (one class or module)
  • Log data must be clear enough to understand what happened
  • Sanitize log data if it comes from user input
  • Never store passwords or session IDs in logs
  • Use cryptographic hash to validate log integrity
  • Ensure a log analysis mechanism exists
📋 Log event data must include: Timestamp, Severity rating, Security tag, User identity, Source IP, Event outcome (success/fail), Event description.
11

Data Protection

Data Protection Rules
  • Temp/cached sensitive data → stored securely, purged ASAP
  • Remove source code comments that reveal sensitive info about the application
  • Protect web server files — only intended files accessible by clients
  • Protect: config files, backups, deployment scripts, temp files
  • Never put sensitive info in URL query strings
  • Disable caching for pages with confidential data: use Cache-Control: no-store + Pragma: no-cache
  • Data in transit must use latest TLS
  • Implement least privilege — users get only what they need
  • Protect server-side source code from being downloaded by users
  • No passwords/connection strings in cleartext on client side
  • Support removal of sensitive data when no longer needed
Things That Reveal Info — Avoid
  • Comments in production code
  • Unnecessary app/system documentation
  • Sensitive info in HTTP GET parameters
  • Auto-complete on sensitive forms
  • Client-side caching of sensitive pages
  • MS Viewstate or Flash embedding of sensitive data
⚠️ Use Referer header carefully when linking to external domains — it can leak sensitive query parameters.
12

Communication Security

TLS Rules
  • Encrypt all sensitive information in transit with TLS
  • TLS certs must be: valid, correct domain, not expired, with intermediate certs
  • Failed TLS must NOT fall back to insecure connection
  • Use TLS for all authenticated access and all sensitive info
  • Use TLS for connections to external systems with sensitive data
  • Use a single standard TLS implementation configured properly
  • Specify character encodings for all connections
  • Filter sensitive parameters from HTTP Referer when linking externally
  • Consistently use HTTPS — don't switch back and forth with HTTP
🔴
Never allow TLS downgrade to HTTP. If a TLS connection fails, the connection should fail entirely — not silently fall back to unencrypted HTTP.
13

System Configuration

Server & Framework Config
  • Servers/frameworks/components on latest approved version with all patches
  • Turn off directory listings
  • Web server/service accounts use least privilege
  • Fail securely when exceptions occur
  • Remove all unnecessary functionality and files
  • Remove test code before production deployment
  • Remove unnecessary info from HTTP response headers (OS version, web server version, framework)
  • Isolate dev environments from production network
  • Implement a software change control system
  • Implement an asset management system
robots.txt & HTTP Methods
  • Don't list individual hidden directories in robots.txt — put them all in a parent directory and disallow the parent
  • Define which HTTP methods (GET/POST) the app supports per page
  • Disable unnecessary HTTP methods (e.g. WebDAV)
  • If HTTP 1.0 and 1.1 both supported — configure consistently
  • Security config store must be exportable in human-readable format for auditing
💡 robots.txt tip: Instead of disallowing /admin, /backup, /private separately — create a parent /hidden/ directory and disallow that one path. This avoids advertising all your hidden paths.
14

Database Security

Database Rules
  • Use strongly-typed parameterized queries (prevents SQL injection)
  • Ensure variables are strongly typed
  • App connects to DB with least privilege
  • Use secure credentials for DB access
  • Connection strings must NOT be hardcoded in the application
  • Connection strings in separate encrypted config file on trusted system
  • Use stored procedures to abstract data access
  • Close the DB connection as soon as possible
  • Change/remove all default DB admin passwords
  • Turn off unnecessary DB functionality (stored procs, services, utilities)
  • Remove unnecessary default vendor content/schemas
  • Disable default accounts not needed for business
  • App connects with different credentials per trust level (user, read-only, guest, admin)
⚠️
Parameterized queries work by separating the SQL structure from the data. The query is compiled first, then data is plugged in — so injected SQL in data can't alter the query structure.

Never use string concatenation to build SQL queries.
15

File Management

File Upload Rules
  • User must be authenticated before uploading any file
  • Limit the types of files that can be uploaded
  • Validate by checking file headers — extension alone is NOT enough
  • Save uploaded files on a separate server, not the web server
  • Prevent web server from executing uploaded files
  • Turn off execution privileges on the upload directory
  • Antivirus + endpoint security on the upload server
  • Validate/remove uploaded files that could be executed/interpreted by web server
  • UNIX: mount target dir as logical drive or use chrooted environment
File Path & Access Rules
  • Never pass directory or file paths directly
  • Use index values mapped to a pre-defined path list
  • Never send the full/absolute file path to the client
  • Never pass user-supplied data to dynamic include functions
  • Don't pass user data to a dynamic redirect
  • If redirect required: accept only validated relative path URLs
  • Web app files and resources must be read-only
  • Scan uploaded files for viruses and malware
  • Use a whitelist of allowed filenames and types for existing files
16

Memory Management

  • Validate input and output for untrusted data
  • Verify buffer is as large as specified
  • Check buffer boundaries in loops — no writing past allocated space
  • With strncpy() — if dest buffer = source size, string may not be NULL-terminated
  • Truncate all input strings to reasonable length before passing to copy/concatenation
  • Explicitly close resources — don't rely on garbage collection
  • Use non-executable stacks when available
  • Avoid known vulnerable functions: printf, strcat, strcpy
  • Properly free allocated memory on function completion and all exit points
17

General Coding Practices

General Secure Coding Rules
  • Use tested and approved managed code rather than new unmanaged code for common tasks
  • Use task-specific built-in APIs for OS operations
  • Never let the app issue OS commands directly or via command shells
  • Use checksums/hashes to verify integrity of libraries, executables, config files
  • Use locking/synchronization to prevent race conditions
  • Protect shared variables from inappropriate concurrent access
  • Explicitly initialize all variables before first use
Elevated Privileges & Third-Party
  • If elevated privileges needed: raise as late as possible, drop as soon as possible
  • Never pass user data to a dynamic execution function
  • Restrict users from generating or altering code
  • Review all secondary apps, third-party code, and libraries for safety
  • For automatic updates: use cryptographic signatures on code + encrypted download channel
  • Understand your language's numeric representation (overflow, precision, truncation)
18

Third-Party Libraries

  • Use checksums to verify integrity of downloaded libraries and scripts
  • Always use the latest stable version of libraries
  • Use a third-party library scanner — e.g. Sonatype, BlackDuck
  • Review third-party code before use
  • Validate business necessity of each third-party component
  • Monitor for newly discovered vulnerabilities in libraries

Required HTTP Security Headers

📌 These headers MUST exist in every web application response. This is commonly tested in exams.
X-Frame-Options
Prevents clickjacking (iframe embedding)
X-Content-Type-Options
Stops MIME type sniffing
Strict-Transport-Security
Forces HTTPS (HSTS)
Content-Security-Policy
Defines trusted content sources (XSS mitigation)
X-Permitted-Cross-Domain-Policies
Controls Flash/PDF cross-domain access
X-XSS-Protection: 1; mode=block
Enables browser XSS filter (blocks attacks)
X-Content-Type-Options: nosniff
Prevents content-type sniffing attacks

Enterprise Secure Coding Guidelines

Your Role as AppSec Expert
  • You are the custodian of secure coding best practices documents/checklists
  • Update them as technology evolves
  • Share via the company's intranet with developers
  • If no secure coding document exists → create one and propose to management
  • Encourage secure coding training for developers
  • Use the checklist both as developer guidelines AND as your manual review checklist
Miscellaneous Security Rules
  • Remove test code before production deployment
  • Don't disclose directory structure in robots.txt
  • Remove unnecessary info from HTTP headers (OS, server, framework versions)
  • If app must elevate privileges → drop them ASAP
  • Properly free all allocated memory at all exit points
  • Implement least privilege everywhere

Risk & Security Principles (OWASP)

Security Goal (CIA Triad)
Confidentiality
Info disclosed only to authorized parties
Integrity
Info is accurate, complete, unaltered
Availability
System is accessible and usable
Risk Formula
Threat Agent → System → Vulnerability → Exploit → Impact

Analogy: Car burglar (threat agent) checks cars (system) for unlocked doors (vulnerability), opens the door (exploit), steals contents (impact).

Where Flaws Are Introduced
  • Not identifying security requirements upfront
  • Conceptual designs with logic errors
  • Poor coding practices introducing technical vulnerabilities
  • Improper deployment
  • Flaws introduced during maintenance/updates
⚠️ Client-side controls provide little security: Hidden fields, client-side input validation, pull-down menus, radio buttons — attackers bypass all of these using proxies (Burp, OWASP WebScarab) or packet capture (WireShark). Always validate server-side.

Quick Reference Cheat Sheet

The Golden Rules — Know These Cold
  • Everything important happens server-side (auth, validation, crypto, logging)
  • Never trust client-side controls
  • Use HTTPS / TLS everywhere, always
  • Passwords: salted hash, no MD5/SHA-1
  • Error messages: never reveal internals
  • Session IDs: random, in cookies only, never in URLs
  • Cookies: Secure + HttpOnly attributes
  • Lock account after 5 failed attempts
  • Use parameterized queries — no hardcoded SQL
  • Input validation: whitelist approach, server-side
  • SAST + Manual review = both required
  • Least privilege everywhere: users, services, DB connections
  • No sensitive info in URLs, logs, error messages
  • Validate file uploads by header, not extension
  • Upload files go to separate server, not web server
  • Remove all test code, comments, debug info before production
  • Deny all access when security config unavailable
  • Use MFA for high-value accounts
