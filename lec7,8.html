Why Web Security?

The Problem

Buffer overflow has become harder due to protections like ASLR (Address Space Layout Randomization) and StackGuard. Web attacks remain the dominant threat.

69% of web apps have vulnerabilities leading to sensitive data exposure. 55% have CSRF flaws. 25% of web apps are still vulnerable to 8 of the OWASP Top 10. (circa 2017)

We are still battling the same issues we have been fighting for decades.

How Does the Web Work?

What is the Web?

The World Wide Web (WWW) is NOT the same as the Internet. It is a subset of the Internet — a collection of websites, pages, and content from around the world.

Client–Server Model

Client — a program on your computer (e.g., web browser: Chrome, Firefox, Safari, IE, Opera, lynx). Sends HTTP Requests.

Server — remote computer running web server software; delivers content back. Examples: Nginx, Apache HTTP Server, Microsoft IIS.

URLs — Uniform Resource Locators

A universal naming scheme for locating content. A subset of URI (Uniform Resource Identifier). Created by Tim Berners-Lee in 1994.

Format: protocol://machine_or_server/directory/file.type
Example: http://www.eecs.tufts.edu/index.html
 • http = Hypertext Transport Protocol
 • www.eecs.tufts.edu = machine + domain
 • index.html = file

URL Protocols (Application Layer of OSI):

httpftptelnet gophermailtofile
Query String: Data passed to the server as key=value pairs after a ?, separated by &.
Example: https://www.google.com/search?q=grand+theft+auto&lr=lang_zh-TW
 • q = query key  • lr = language key
HTTPS = HTTP + Transport Layer Security (TLS) — encrypted!

HTTP — HyperText Transfer Protocol

HTTP Basics

Lives on the Application Layer of the OSI Model. Works as a request–response protocol (like question-and-answer). It is:

Plaintext (insecure) Stateless RFC 2616

HTTP Request

Two parts: Header (details — like an envelope) and Body (data sent, including query string key-value pairs).

Request Methods:

GET — download / typing URL in browser POST — form submission PUT — upload DELETE — delete

HTTP Response Status Codes

Two parts: Header (characteristics of data) and Body (content: HTML, text, JSON…)

200OK 301Moved Permanently 302Found (Redirected) 401Unauthorized 403Forbidden 404Not Found 500Internal Server Error

HTML & JavaScript

HTML = structure of the page. JavaScript = can run on client-side AND server-side. In this course we focus on client-side JavaScript to abuse web pages.

HTTP Cookies

What is a Cookie?

A small amount of data sent by the server to the browser, which sends it back on future requests to the same site. Data is stored as key-value pairs. RFC 2109.

Max size: 4 KB

Max total cookies: 300

Max per domain: 20 cookies

Uses: authentication, user tracking, shopping cart, preferences

Can be persistent (survive browser close)

Stored as a file on the client

Cookie Rules

Same-Origin Policy: a domain CANNOT access a cookie set by another domain!

All cookies set by server are sent back to the server during every interaction.

Cookie Manipulation via JavaScript

Set a cookie: document.cookie = "key=value";

Read all cookies: allCookies = document.cookie;

Get a specific value: find it inside document.cookie

Web Proxies — Essential Attack Tool

What is a Web Proxy?

A tool that intercepts HTTP requests and responses between your browser and the server. Lets you: modify header fields, modify the request body, change query strings and data, and log/record all HTTP(S) traffic.

Burp Suite

Java-based. Available on Kali Linux. The most popular pen-test proxy.

Free: intercept browser traffic via man-in-the-middle proxy.

Paid: automated crawler and scanner for 100+ vulnerabilities including all OWASP Top 10.

OWASP ZAP (Zed Attack Proxy)

Free and open-source. Java-based. Similar to Burp Suite.

Includes a vulnerability scanner and spider for automated discovery.

Tamper Data (Firefox Add-on)

Simple Firefox add-on. Can intercept and modify HTTP request parameters. Less feature-rich than Burp or ZAP.

mitmproxy

Command-line based man-in-the-middle proxy. Open-source. Good for scripting and automation.

Using Burp Suite (Hackme Playground Workflow)

Turn on Burp → intercept the HTTP request → under Proxy > Intercept, modify field values (e.g., price, fullname, beverage) → press Forward to send altered request to server.

Basic Vulnerabilities

Principle of Least Privilege — Or Lack Thereof

The issue: connecting to a database as root or administrator — the account that can do anything.

Bad code example: $conn = mysql_connect("127.0.0.1", "root", "pass"); — whoever gets the root password gets the keys to the kingdom.

Defense: create a separate DB user for the web app with access only to what it needs (least privilege = access only to information, operations, and resources necessary to its legitimate purpose).

Hard-Coded Credentials

The issue: usernames, passwords, or API keys written directly into source code.

Worst case: pushing that source code to a public GitHub repo — credentials instantly exposed!

Defense: never hard-code credentials in source code. Store them in system environment variables instead.

Cross-Site Scripting (XSS)

Cross-Site Scripting (XSS)

OWASP A7:2017

The idea: instead of entering normal data in form fields, enter JavaScript code that gets executed on other users' browsers.

Where to attack:

Anywhere user input is echoed to other users — e.g., message boards, comment sections, search fields.

Consequences:

• Show fraudulent web content to all users
• Steal cookie information
• Inject malicious code
• Display annoying pop-ups

Important: XSS is NOT the same as phishing. XSS is embedded in the actual trusted website.

How to embed script in HTML: using the <script> tag.

XSS Payloads:

<script>alert('XSS');</script>

<script>window.document.getElementById("SOME_ID").innerHTML='<img src="SOME_URL" />';</script>

Defense:

Remove ability for data to be interpreted as code. Escape angle brackets:

Change < to &lt; Change > to &gt; Draconian: filter ALL special characters from user input

SQL Injection

SQL Injection

OWASP A1:2017 — Injection

The idea: twist SQL queries via user input to access or modify data you shouldn't have access to. This is really bad!

Where to attack: web apps with a database — form fields or URL parameters.

The culprit: the single quote '

How to detect: errors displayed on the page when you inject a quote.

Blind SQL Injection: asks the database true/false questions and infers the answer from the app's behavior — no error messages needed.

Classic Example:

-- Normal (requires correct password):
SELECT id FROM users WHERE username='batman' AND password='foo';

-- With injection payload: WHATEVER' OR '1'='1
SELECT id FROM users WHERE username='batman' AND password='WHATEVER' OR '1'='1';
-- Always returns a result → bypass login!

Defense:

Filter out ' and " characters Use Prepared Statements Apply least privilege to the DB user

Tool: sqlmap

Open-source pen-testing tool that automates detecting and exploiting SQL injection flaws and can take over database servers. Usage: sqlmap -u <target_url>

Bypassing Input Restrictions

Bypassing Form Restrictions

Client-Side Bypass

The idea: form restrictions (maxlength, dropdown choices, etc.) are enforced only in the browser. A proxy bypasses them entirely.

Conducting the attack: use a proxy (Burp Suite), intercept the HTTP request, modify any field values, forward the altered request to the server.

Defense: always perform server-side input validation — never rely on client-side checks alone.

Hidden Form Fields

Form Tampering

All hidden fields are sent to the server on form submission. They are easy to identify: <input type="hidden" name="...">

Bad mistake: storing sensitive information in hidden fields — e.g., account number, password, product price. Historical exploit: buying a plasma TV for $0.99 by modifying the price field.

Conducting attack: intercept with proxy → modify hidden field values → forward.

Defense: never store important information in hidden form fields.

Cookie Tampering

Cookie Attack

The idea: intercept the HTTP request with a proxy, modify cookie values (e.g., change isAdmin=false to isAdmin=true), and send to server.

Defense: never store sensitive data in cookies such as passwords or admin-check booleans. Validate on the server side.

Cross-Site Request Forgery (CSRF / XSRF)

Cross-Site Request Forgery (CSRF)

Think: Forgery

The idea: exploits the fact that you are already logged into a website. The attacker tricks your browser into performing actions on the site on your behalf, without your knowledge or consent.

Key difference from XSS: CSRF does NOT require JavaScript! It just needs a browser that is already authenticated.

Real Example (YouTube, ~2008): an attacker could add a video to any logged-in user's Favorites simply by embedding an <img> tag with the action URL. No JS needed — the browser automatically sent the authenticated request.

Defense:

Verify requests come from the same origin Require user interaction for transactions Append unpredictable challenge tokens (CSRF tokens) to each request, tied to user session

Directory Traversal (Path Traversal)

Directory / Path Traversal

Also: Path Traversal

The idea: access files outside the website's root directory, including sensitive system files like password and configuration files.

Method: manipulate URL variables using ../ (dot-dot-slash) sequences or absolute paths.
Example: http://somedomain/../../../../etc/passwd — this should NOT display the passwd file, but a vulnerable server will!

Real Case: Miele dishwasher (IoT) — its web server was vulnerable to directory traversal via /../../../etc/shadow, exposing Linux password hashes.

Why it still happens: web server misconfiguration or developer laziness.

Defense:

Input validation — filter out /, ., and % Proper web server configuration

Command Injection (Command Execution)

Command Injection

OS-Level Attack

The idea: trick the web server into running arbitrary system commands (e.g., ls, cat, ping, more) through a vulnerable URL parameter or input field.

Before (normal): http://site/cgi-bin/userData.pl?doc=user1.txt
After (attack!): http://site/cgi-bin/userData.pl?doc=/bin/ls — runs ls on the server!

Dangerous ("dirty") functions by language:

Java: Runtime.exec()

C/C++: system, exec, ShellExecute

Python: exec, eval, os.system, os.popen, subprocess.popen, subprocess.call

PHP: system, shell_exec, exec, proc_open, eval

Defense: input validation, filter out special characters, avoid using dangerous functions with user input.

15

Remote & Local File Inclusion (RFI / LFI)

File Inclusion Attacks

LFI & RFI

The idea: the app accepts a file path or URL as user input and uses it directly — the input is trusted without validation.

Local File Inclusion (LFI)

Similar to directory traversal. The attacker selects a file on the local server to display.

Normal: ?page=home.php
Attack: ?page=/etc/passwd

Remote File Inclusion (RFI)

The attacker uses a remote URL as input, loading an external resource into the page.

Normal: ?page=home.php
Attack: ?page=https://google.com

Defense:

Input validation — filter /, ., % In PHP: set allow_url_fopen = Off and allow_url_include = Off in php.ini

The Moral of the Story

NEVER TRUST
USER INPUT.

This is the root cause of XSS, SQL Injection, Command Injection, Directory Traversal, File Inclusion, Hidden Form Tampering, and more.

Validate on the server Sanitize all inputs Filter special characters Escape output Use prepared statements Least privilege
