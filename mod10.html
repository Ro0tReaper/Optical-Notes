10.1 Device Discovery with CDP Cisco Proprietary · Layer 2
CDP (Cisco Discovery Protocol) is a Cisco-proprietary Layer 2 protocol. It gathers info about directly connected Cisco devices — media and protocol independent. Runs on routers, switches, and access servers. Devices send periodic advertisements sharing device type, name, and interface info.
  • Enabled by default on all Cisco devices
  • Works on all Cisco devices: routers, switches, access servers
  • Only discovers directly connected neighbors (not routed — Layer 2 only)
  • Does not require IP connectivity to discover neighbors

Commands — Enable / Disable

Router(config)# cdp run ← enable CDP globally (default: on) Router(config)# no cdp run ← disable CDP on ALL interfaces globally Router(config-if)# cdp enable ← enable CDP on a specific interface Router(config-if)# no cdp enable ← disable CDP on a specific interface only (CDP still runs on device, just not that port)

Commands — Verify & Discover

R1# show cdp ← verify CDP is running, shows timers R1# show cdp interface ← show which interfaces have CDP enabled + status R1# show cdp neighbors ← list all directly connected neighbors R1# show cdp neighbors detail ← includes IP address, IOS version, full detail

Output: show cdp neighbors

R1# show cdp neighbors Capability Codes: R - Router, T - Trans Bridge, B - Source Route Bridge S - Switch, H - Host, I - IGMP, r - Repeater, P - Phone, D - Remote, C - CVTA, M - Two-port Mac Relay Device ID Local Intrfce Holdtme Capability Platform Port ID S1 Gig 0/0/1 179 S I WS-C3560- Fas 0/5

Capability Codes

  • R — Router
  • T — Trans Bridge
  • B — Source Route Bridge
  • S — Switch
  • H — Host
  • I — IGMP
  • r — Repeater
  • P — Phone
  • D — Remote
  • C — CVTA
  • M — Two-port Mac Relay

Output Fields

  • Device ID — neighbor hostname
  • Local Intrfce — your port connected to it
  • Holdtme — seconds until entry expires
  • Capability — letter codes (see left)
  • Platform — hardware model
  • Port ID — neighbor's port facing you

Output: show cdp neighbors detail

R1# show cdp neighbors detail ------------------------- Device ID: S1 Entry address(es): IP address: 192.168.1.2 ← IP not shown in basic neighbors Platform: cisco WS-C3560-24TS, Capabilities: Switch IGMP Interface: GigabitEthernet0/0/1, Port ID (outgoing port): FastEthernet0/5 Holdtime : 136 sec
Use show cdp neighbors detail when you need the neighbor's IP address — it's not shown in the basic show cdp neighbors output.
10.2 Device Discovery with LLDP Vendor-Neutral · Layer 2
LLDP (Link Layer Discovery Protocol) is the open-standard, vendor-neutral equivalent of CDP. Works with any vendor's network devices: routers, switches, and wireless LAN access points. Advertises identity and capabilities; receives info from physically connected Layer 2 devices.
  • Vendor-neutral — not Cisco-specific; works across multi-vendor environments
  • Also Layer 2, also sends neighbor advertisements
  • May or may not be enabled by default — check first with show lldp
  • LLDP transmit and receive must be configured separately per interface

Commands — Enable / Disable / Verify

Switch(config)# lldp run ← enable LLDP globally Switch(config)# no lldp run ← disable LLDP globally Switch(config-if)# lldp transmit ← allow sending LLDP packets on this interface Switch(config-if)# lldp receive ← allow receiving LLDP packets on this interface Switch# show lldp ← verify LLDP is active + global timers

show lldp Output

Switch# show lldp Global LLDP Information: Status: ACTIVE LLDP advertisements are sent every 30 seconds LLDP hold time advertised is 120 seconds LLDP interface reinitialisation delay is 2 seconds

Commands — Discover Neighbors

S1# show lldp neighbors ← list neighbors with capability codes S1# show lldp neighbors detail ← adds IOS version, IP address, full capabilities

show lldp neighbors Output

S1# show lldp neighbors Capability codes: (R) Router, (B) Bridge, (T) Telephone, (C) DOCSIS Cable Device (W) WLAN Access Point, (P) Repeater, (S) Station, (O) Other Device ID Local Intf Hold-time Capability Port ID R1 Fa0/5 117 R Gi0/0/1 S2 Fa0/1 112 B Fa0/1 Total entries displayed: 2

LLDP Capability Codes

  • R — Router
  • B — Bridge (Switch)
  • T — Telephone
  • C — DOCSIS Cable Device
  • W — WLAN Access Point
  • P — Repeater
  • S — Station
  • O — Other

CDP vs LLDP

  • CDP = Cisco only / LLDP = any vendor
  • Both are Layer 2
  • Both have basic + detail show commands
  • LLDP TX and RX configured separately
  • LLDP detail shows IOS version
  • LLDP timers: 30s send / 120s hold / 2s reinit
10.3 NTP — Network Time Protocol UDP 123 · RFC 1305
NTP synchronizes clocks across all network devices. Without synchronized time, you cannot determine the order of events or correlate logs. Uses UDP port 123, documented in RFC 1305. Can sync to a private master clock or a public NTP server on the internet.

Method 1: Manual Clock Set (small networks only)

R1# clock set 20:36:00 nov 15 2019 Output: *Nov 15 20:36:00.000: %SYS-6-CLOCKUPDATE: System clock has been updated R1# show clock ← shows current time (basic) R1# show clock detail ← shows time AND "Time source is user configuration"
Manual configuration doesn't scale. As the network grows, use NTP instead — it keeps all devices synchronized automatically.

NTP Stratum Hierarchy

  • NTP uses a hierarchical system — each level is called a stratum
  • Stratum level = number of hop counts from the authoritative time source
  • Max hop count = 15. Stratum 16 = device is unsynchronized
  • Devices at the same stratum can be configured as peers for backup/verification
StratumWhat it isExample
0Authoritative source — atomic clock / GPS. High precision, little/no delay. Not on network directly.GPS clock, atomic clock
1Directly connected to stratum 0. Primary network time standard.NTP server synced to GPS
2Syncs via NTP packets from stratum 1. Can also serve stratum 3 devices.Corporate NTP server
3+Each hop adds 1 to stratum. Syncs from the level above.Router, switch
16Unsynchronized — do not use for time.Device not synced

Method 2: Configure NTP (recommended)

-- Step 1: Check current time source before NTP -- R1# show clock detail 20:55:10.207 UTC Fri Nov 15 2019 Time source is user configuration ← manually set -- Step 2: Point R1 to NTP server -- R1(config)# ntp server 209.165.200.225 -- Step 3: Verify time source changed -- R1# show clock detail 21:01:34.563 UTC Fri Nov 15 2019 Time source is NTP ← now synced via NTP

Verify NTP Associations

R1# show ntp associations address ref clock st when poll each delay offset disp *~209.165.200.225 .GPS. 1 61 64 377 0.481 7.480 4.261 ↑ * = sys.peer (selected) ~ = configured st = stratum of the server (1), when = seconds since last response poll = polling interval (sec), delay/offset/disp = timing quality metrics R1# show ntp status Clock is synchronized, stratum 2, reference is 209.165.200.225 ← R1 is now stratum 2 (one hop from the stratum 1 GPS server)

Cascade: Sync a Switch from R1

S1(config)# ntp server 192.168.1.1 ← point S1 to R1 S1# show ntp associations address ref clock st when poll reach delay offset disp *~192.168.1.1 209.165.200.225 2 12 64 377 1.066 13.616 3.840 ← S1 sees R1 as stratum 2 S1# show ntp status Clock is synchronized, stratum 3, reference is 192.168.1.1 ← S1 is now stratum 3 (can serve stratum 4 devices)
Chain rule: if server is stratum N, the client becomes stratum N+1. R1 → stratum 2, S1 syncing from R1 → stratum 3.
10.4 SNMP — Simple Network Management Protocol UDP 161 (poll) · UDP 162 (trap)
SNMP is an Application Layer protocol that lets admins monitor and manage network devices. It provides a message format for communication between managers and agents. Manager polls agents on UDP 161. Agents send traps to manager on UDP 162.

Three Core Components

SNMP Manager

  • Part of NMS (Network Management System)
  • Collects info using get
  • Changes config using set
  • Receives unsolicited traps

SNMP Agent

  • Runs on managed device
  • Collects + stores data in MIB locally
  • Responds to manager get/set requests
  • Sends traps when events occur

MIB

  • Management Information Base
  • Database of variables on the device
  • Organized hierarchically using OIDs
  • Available to authenticated remote users

SNMP Operations (Manager ↔ Agent)

OperationDirectionDescription
get-requestManager → AgentRetrieve value of one specific MIB variable
get-next-requestManager → AgentSequential search through a table — no need to know exact variable name
get-bulk-requestManager → AgentRetrieve large blocks at once (multiple rows). SNMPv2c and later only.
get-responseAgent → ManagerReply to any get-request, get-next-request, or set-request
set-requestManager → AgentWrite a value to a specific MIB variable (can also trigger actions like rebooting)
trapAgent → ManagerUnsolicited notification — agent pushes alert when event occurs (e.g. interface down)

SNMP Traps

  • Traps are unsolicited — agent initiates, no polling needed
  • Reduce network/agent overhead by eliminating polling for certain events
  • NMS can respond: send text message, pop up window, or turn device icon red in GUI

SNMP Versions

VersionRFC(s)AuthenticationSecurity
SNMPv1RFC 1157Community string (plaintext)Weak — should not be used (security risks)
SNMPv2cRFCs 1901–1908Community string (plaintext)Adds bulk retrieval + detailed error messages. Many orgs use read-only mode only.
SNMPv3RFCs 3410–3415Username + HMAC-MD5 or HMAC-SHAEncryption: DES, 3DES, or AES. Use this version.

Community Strings (v1 and v2c)

  • Act as plaintext passwords for MIB access — authenticate access to MIB objects
  • ro (read-only) — can read MIB variables, cannot change them. Used by most orgs in v2c for safety.
  • rw (read-write) — full read and write access to all MIB objects

MIB Object IDs (OIDs)

  • MIB organizes variables hierarchically in a tree — each variable has a unique OID
  • OIDs can be expressed in words or numbers
  • Public branches: defined by RFCs, common to many devices
  • Private branches: vendor-specific (e.g. Cisco adds its own subtree)
Cisco OID tree path: iso(1) → org(3) → dod(6) → internet(1) → private(4) → enterprises(1) → cisco(9) Cisco OID = 1.3.6.1.4.1.9 Branches under cisco(9): └── local variables (2) │ └── interface group (2) └── cisco mgmt (9) └── cisco flash group (10)

SNMP Polling — snmpget Utility

  • One use case: poll CPU utilization over time — compile on NMS and graph to create baseline
  • snmpget retrieves real-time data manually, or NMS runs reports automatically
snmpget syntax: version community IP-address OID snmpget -v2c -c community 10.250.250.14 .1.3.6.1.4.1.9.2.1.58.0 SNMPv2-SMI::enterprises.9.2.1.58.0 = INTEGER: 11 ← CPU value returned Fields: -v2c = version, -c community = community string, IP = device to poll, OID = variable to read
Cisco SNMP Object Navigator at cisco.com lets you look up any OID by name or number — translates long numeric OIDs into readable variable names and descriptions.
10.5 Syslog UDP 514
Syslog uses UDP port 514 to send event notification messages across IP networks to event message collectors. Provides: (1) gathering logs for monitoring/troubleshooting, (2) selecting what types of messages are captured, (3) specifying destinations for messages.

How Syslog Works

  • Syslog process starts locally — sends system messages and debug output to local logging
  • Configuration can forward messages across the network to an external syslog server (retrieve logs without accessing device directly)
  • Alternatively, messages go to an internal buffer — only viewable via CLI of that device
  • Admin specifies which message types go to which destinations

Syslog Destinations

Destinations

  • Logging buffer — RAM inside router/switch
  • Console line — shown on console connection
  • Terminal line — shown on VTY (SSH/Telnet)
  • Syslog server — centralized external server

Three Primary Functions

  • Gather logs for monitoring & troubleshooting
  • Select the type of logging info captured
  • Specify destinations for captured messages

Severity Levels — lower number = more critical

LevelNameExplanation
0EmergencySystem unusable
1AlertImmediate action needed
2CriticalCritical condition
3ErrorError condition
4WarningWarning condition
5NotificationNormal, but significant condition
6InformationalInformational message
7DebuggingDebug output — lowest priority

Syslog Message Format

%FACILITY-SEVERITY-MNEMONIC: description Example: %LINK-3-UPDOWN: Interface Port-channel1, changed state to up ↑ facility ↑ severity (error) ↑ mnemonic

Common Syslog Facilities (Cisco IOS)

  • IP — IP protocol messages
  • OSPF — OSPF routing protocol
  • SYS — operating system
  • IPsec — IP security
  • IF — Interface IP

Timestamps — not enabled by default

-- WITHOUT timestamps (default) -- R1(config-if)# shutdown %LINK-5-CHANGED: Interface GigabitEthernet0/0/0, changed state to administratively down %LINEPROTO-5-UPDOWN: Line protocol on Interface GigabitEthernet0/0/0, changed state to down ^ No time shown — cannot tell WHEN this happened -- Enable timestamps -- R1(config)# service timestamps log datetime -- WITH timestamps (after enabling) -- R1(config-if)# no shutdown *Mar 1 11:52:42: %LINK-3-UPDOWN: Interface GigabitEthernet0/0/0, changed state to down *Mar 1 11:52:45: %LINK-3-UPDOWN: Interface GigabitEthernet0/0/0, changed state to up *Mar 1 11:52:46: %LINEPROTO-5-UPDOWN: Line protocol on Interface GigabitEthernet0/0/0, changed state to up
Always enable service timestamps log datetime when forwarding to a syslog server — otherwise there is no record of when the event occurred.
10.6 Router & Switch File Maintenance Backup · Restore · Password Recovery

Cisco IOS File System (IFS)

  • Allows navigating directories, listing files, creating subdirectories in flash or disk
  • Available directories depend on the device model
  • Asterisk (*) in show file systems = current default file system
  • Pound sign (#) = bootable disk. Both default to the flash file system.
Router# show file systems ← list all filesystems; * = default, # = bootable Router# dir ← list contents of current (default = flash) last file listed = current IOS image running in RAM Router# cd nvram: ← change directory to NVRAM Router# pwd ← print working directory (confirm location) Router# dir ← now lists NVRAM; startup-config is here

Backup Method 1: Tera Term (text file)

  1. File menu → click Log
  2. Choose location to save. Tera Term begins capturing all terminal text.
  3. Execute show running-config or show startup-config — output goes to the file
  4. When done, select Close in the Tera Term: Log window
  5. View the file to verify it was not corrupted

Restore Method 1: Tera Term (text file)

Before restoring: edit the file — remove encrypted passwords (replace with plaintext), remove non-command text like --More-- and IOS messages. Add enable and configure terminal at the top, or manually enter global config mode first.
  1. File menu → click Send File
  2. Locate and select the config file, click Open
  3. Tera Term pastes the file into the device — becomes the running configuration

Backup/Restore Method 2: TFTP

-- BACKUP to TFTP -- R1# copy running-config tftp Remote host []? 192.168.10.254 Name of the configuration file to write[R1-config]? R1-Jan-2019 Write file R1-Jan-2019 to 192.168.10.254? [confirm] Writing R1-Jan-2019 !!!!!! [OK] -- RESTORE from TFTP -- R1# copy tftp running-config (prompts for TFTP server IP, filename, then applies it)

Backup/Restore Method 3: USB Flash Drive

  • USB storage provides optional secondary storage and additional boot device
  • First: run show file systems to verify USB is present and confirm its name (e.g. usbflash0:)
-- BACKUP to USB -- R1# copy running-config usbflash0:/ Destination filename [running-config]? R1-Config %Warning: There is a file already existing with this name Do you want to over write? [confirm] ← prompts if file exists 5024 bytes copied in 1.796 secs (2797 bytes/sec) -- VIEW USB contents -- R1# dir usbflash0:/ ← list files on USB R1# more usbflash0:/R1-Config ← view file contents -- RESTORE from USB (edit file first with text editor) -- R1# copy usbflash0:/R1-Config running-config

Password Recovery Procedure

  • Used when passwords are lost/unknown. For encrypted passwords (enable secret), the password must be replaced — it cannot be recovered, only overwritten.
  • Exact procedure varies by device model — but the principle is always the same 6 steps.
  1. Enter ROMMON mode — use a break sequence during boot, OR remove external flash memory while device is powered off. Prompt: rommon 1 >
  2. Change config register: confreg 0x2142 then reset — causes device to ignore startup-config on next boot. Enter break sequence AGAIN while the device reboots and decompresses IOS.
  3. Copy startup to running: copy startup-config running-config — loads old config into RAM without it being the boot config
  4. Change the password: enable secret cisco (use a strong password in practice)
  5. Restore register and save: config-register 0x2102 then copy running-config startup-config
  6. Reload: reload
CRITICAL: Do NOT run copy running-config startup-config before step 3 (copying startup to running). Doing so will erase your original startup configuration permanently.
-- ROMMON commands -- rommon 1 > confreg 0x2142 ← ignore startup-config on boot rommon 2 > reset ← reboot -- After reboot (now in privileged EXEC, no password needed) -- Router# copy startup-config running-config R1(config)# enable secret cisco R1(config)# config-register 0x2102 ← restore normal boot register R1(config)# end R1# copy running-config startup-config R1# reload
10.7 IOS Image Management TFTP · Flash · boot system
Store IOS images on a central TFTP server for backup. If flash is corrupted or accidentally erased, restore the image over the network. TFTP server can be another router, a workstation, or a host system.
  • Production networks span wide areas — keep backup IOS images always
  • TFTP allows image and configuration uploads/downloads over the network
  • Controls the number of IOS versions and configs that must be maintained

Backup IOS Image → TFTP Server

  1. Ping the TFTP server — verify connectivity before doing anything
  2. Check image size: show flash0: — verify TFTP server has enough disk space to hold the image
  3. Copy: copy source-url destination-url — prompted for source filename, TFTP IP, and destination filename. Transfer begins.

Copy IOS Image from TFTP → Device

  1. Ping the TFTP server — verify connectivity
  2. Check free flash space: show flash: — compare free space against new image file size
  3. Copy from TFTP: copy tftp: flash: — prompted for TFTP IP, source filename, destination filename
R1# copy tftp: flash: Address or name of remote host []? 2001:DB8:CAFE:100::99 Source filename []? isr4200-universalk9_ias.16.09.04.SPA.bin Destination filename [isr4200-universalk9_ias.16.09.04.SPA.bin]? Accessing tftp://2001:DB8:CAFE:100::99/isr4200-universalk9_ias.16.09.04.SPA.bin... Loading isr4200-universalk9_ias.16.09.04.SPA.bin !!!!!!!!!!!!!! [OK - 517153193 bytes] 517153193 bytes copied in 868.128 secs (265652 bytes/sec)

boot system Command — Set Which IOS to Load

  • During startup, bootstrap code parses NVRAM startup-config for boot system commands
  • Multiple boot system commands can be entered in sequence — creates a fault-tolerant boot plan (tries first, falls back to next)
  • If no boot system commands exist → router defaults to loading the first valid IOS image in flash
-- After copying new image, tell router to use it -- R1(config)# boot system flash0:isr4200-universalk9_ias.16.09.04.SPA.bin R1(config)# exit R1# copy running-config startup-config ← save so boot system command persists R1# reload ← reboot to load the new image
Always save the config before reloading — boot system only takes effect on the next boot, and it must be in startup-config to survive the reload.
