Introduction

What is Cloud Networking?

Think of cloud networking as the internal plumbing and road system inside a massive factory (the data center). The factory makes products (cloud services) used by billions of people — Facebook, Netflix, Google, Amazon, Dropbox. But what makes those services fast and reliable is not just the servers — it's how those servers talk to each other inside the factory. Cloud networking is that internal communication infrastructure.

The cloud services we use every day — Facebook, Twitter, Google, Netflix, Amazon, Dropbox, Coursera — are all powered by massive data centers. These data centers contain thousands to hundreds of thousands of servers. The network inside those data centers is what makes it possible for all those servers to work together to serve millions of users simultaneously.

The lecture focuses on networking within the data center — not the carrier networks (ISPs, fiber backbones) that connect users to the data center. Specifically: the network equipment, software, and standards used to build networks inside large cloud data centers.

🔀
Introduction

The Scatter-Gather Traffic Pattern

When you type a search query into Google, your request goes to one "front-end" server. That server then broadcasts your query to hundreds of index servers simultaneously (scatter). Each index server quickly searches its portion of the web index and sends back a partial result. The front-end collects all the partial results (gather), ranks them, and returns the final page to you — all in under a second.

Scatter-gather is the dominant traffic pattern in cloud data centers, especially for search, recommendation, and distributed computation workloads:

  • Scatter: One request is fanned out (scattered) to many servers simultaneously. Each server processes a portion of the task in parallel.
  • Gather: All servers send their partial results back to the originating server, which aggregates them into a final response.
Why this matters for networking: Scatter-gather creates intense, simultaneous bursts of traffic flowing in many directions at once — between servers across different racks. This is called east-west traffic (server-to-server). Traditional networks were designed for north-south traffic (client-to-server). Cloud data center networks must be redesigned to handle massive east-west bursts efficiently.

This need for efficient, cost-effective networks that can handle scatter-gather traffic is the fundamental driver behind all the network topology innovations in this lecture.

Traffic

Traffic Volume — Growing Explosively

In 2008, the total traffic generated by all servers in Google's data centers was at a certain baseline. By 2014, that number had grown by 50x. That's not 50% more — that's fifty times more. It grew faster than any individual server's speed, and several orders of magnitude larger than internet traffic that leaves the data center.

Data from Google's "Jupiter Rising" paper (ACM SIGCOMM 2015) shows that internal data center traffic has grown 50x from 2008 to 2014. Three key insights from this data:

  • Machine-to-machine traffic dominates: Most of this traffic is servers talking to other servers — not users talking to servers. The scatter-gather pattern generates enormous internal traffic for every single user request.
  • Several orders of magnitude larger than internet traffic: The traffic that actually leaves the data center to reach users is tiny compared to what flows internally. For every byte you receive from a cloud service, many more bytes were exchanged between servers inside the data center to produce it.
  • Implication: You can't use traditional network designs. You need efficient, high-capacity, scalable internal networks — this drove all the innovations described in the Physical Structure section.

Think of a city's road system. Most car trips are short — within the same neighborhood. A smaller fraction go across town. Very few go to another city. Data center traffic follows the same pattern: most traffic stays very local, and only a fraction leaves the data center entirely.

Traffic

Concurrent Flows — Massive Parallelism

Facebook research (SIGCOMM'15) shows that servers maintain large numbers of simultaneous connections at all times:

  • Web servers and cache hosts have 100s to 1000s of concurrent connections — serving many users and fetching from many backends simultaneously.
  • Hadoop/compute nodes have approximately 25 concurrent connections on average.

Microsoft Research data (IMC'09, 1500-server cluster) reveals the communication pattern:

  • Median server communicates with 2 other servers within its own rack
  • And 4 servers outside its rack
Why this matters: With 100s to 1000s of concurrent flows per server, and thousands of servers, the network must handle millions of simultaneous flows. Each flow needs a path through the network fabric. Poor network design creates bottlenecks at shared links or switches — causing exactly the congestion problems described next.
⏱️
Traffic

Flows Arrival Rate — Extremely Fast

Facebook's data shows that new network flows arrive with a median inter-arrival time of approximately 2ms. That means a new connection is being established every 2 milliseconds on average, per server.

The Microsoft 1500-server cluster data shows a flow arrival rate that is less than 0.1× Facebook's rate — meaning Facebook's infrastructure sees flows arriving more than 10× faster, reflecting its much larger scale.

Implication: The network must be able to establish, route, and tear down connections at microsecond to millisecond timescales. Centralized flow-level control (where a central controller manages every single flow) becomes very difficult at this speed — flows arrive faster than a central controller can react. This is one reason why centralized control at the flow level may be difficult in large data centers.

Traffic

Flows Size — Mostly Small, Some Giants

Think of network flows like packages at a shipping depot. Most packages are tiny envelopes (quick to process). A small percentage are huge freight containers (take a long time and lots of resources). The mix of tiny and giant flows — called "mice and elephants" — creates challenges: if you treat both the same, the giants block the mice; if you prioritize differently, you need complex management.

Facebook data (Hadoop and Caching workloads):

  • Hadoop: Median flow size is less than 1KB — extremely small. Only less than 5% of flows exceed 1MB or last longer than 100 seconds. Most Hadoop flows are tiny control messages.
  • Caching: Most flows are long-lived (persistent connections) but internally bursty — quiet for periods, then suddenly sending large amounts.

Microsoft Research (1500-server cluster):

  • Over 80% of flows last less than 10 seconds
  • Over 50% of all bytes transferred are in flows lasting less than 25 seconds
Mice and Elephants: The vast majority of flows (by count) are tiny and short-lived. But a small number of large flows carry a disproportionate amount of data. Network design must handle both simultaneously — small latency-sensitive flows AND large bandwidth-hungry flows — without them interfering with each other.

Networking Implications — The 5 Big Problems

Given everything we know about traffic — it's huge, mostly internal, massively parallel, fast-arriving, and mixed in size — what do network designers actually have to worry about? The lecture identifies 5 specific challenges that drive every design decision.

1 Data center internal traffic is big 50× growth since 2008; machine-to-machine traffic far exceeds internet-facing traffic Need high-bandwidth internal fabrics with lots of parallel paths; can't use traditional campus network designs
2 Tight deadline for network I/O Scatter-gather means the SLOWEST server determines the total response time. If 1 of 100 servers is slow, the whole query is slow. Need distributed or hardware-level forwarding for individual flows.
The tight deadline problem illustrated: Assume each server independently has a 1% chance of responding slowly (≥1s). With 1 server: 1% of responses are slow. With 100 servers (scatter-gather): the probability that AT LEAST ONE is slow = 1 - (0.99)^100 ≈ 63%. So what was a 1% problem per server becomes a 63% problem for the aggregate query. This is why network latency is so critical in distributed cloud applications.

Cisco Global Cloud Index — Key Stats

The "Cisco Global Cloud Index: Forecast and Methodology, 2012–2017" provided these key predictions:

  • Data center traffic grows 25% per year — at minimum — through 2017.
  • By 2017, over 2/3 of all data center traffic will originate from cloud-based data centers.
  • 76% of cloud data center traffic flows between devices within the cloud data center — confirming that internal (east-west) traffic dominates.
  • Server virtualization will have a large impact on cloud data center networks — each physical server now hosts many VMs, each with its own network identity, multiplying the number of virtual endpoints and flows the network must handle.
What virtualization does to traffic: Before virtualization: 1 server = 1 network endpoint = 1 MAC address. After virtualization: 1 server = 10 VMs = 10 virtual network endpoints = 10 MAC addresses + 10 IP addresses. The network now sees 10× the logical devices, 10× the flows, and VMs can migrate between physical servers — their network identity must follow them. This fundamentally changes what the network must support.

Physical Structure

What is a Data Center?

A data center is like a very special building — not just an office, but a purpose-built facility where every detail (power, cooling, cabling, security) is engineered to keep computers running 24/7/365 without failure. It's the physical home for cloud computing.

A data center is a facility designed to house, manage, and support computing resources that are critical for one or more organizations. A modern cloud data center includes:

Physical Structure

Physical Network Layout — Three Approaches

How do you connect servers in a rack to the network? There are three approaches, each with different trade-offs. Think of it like deciding where to put the traffic on-ramp for each block of a city: put it at the end of each block (ToR), at the end of the street (EoR), or use a smarter ramp system that combines both (Fabric Extender).

The physical layout question is: where do you place the first network switch that servers connect to? Three options:

1. ToR — Top of Rack

A network switch sits at the top of each server rack. All servers in that rack connect via short copper cables to this switch (1–3 meters). The switch then uplinks via fiber optic cables to aggregation/core switches above.

2. EoR — End of Row

Servers in all racks of a row run copper cables all the way to a switch located at the end of the row (last rack). The EoR switch serves an entire row of server racks. Cables can be 10–20+ meters long.

3. Fabric Extender (FEX)

A "dumb" hardware device (fabric extender — not a full switch) sits at the top of each rack. It connects via fiber to a Controlling Bridge switch at the end of the row. The controlling bridge has all the intelligence; the FEX is just a port multiplier. From the network's perspective, all the FEX ports appear as if they're directly on the controlling bridge.

⚖️
Physical Structure

ToR — Pros and Cons

✅ Why ToR?

  • Copper stays in-rack: Short copper cables (cheap, low power) connect servers to ToR switch. No expensive long copper runs across the data center.
  • Supports east-west traffic: Optimized for server-to-server communication — critical for cloud workloads
  • Lower cabling costs: Dramatically less cable infrastructure; cleaner cable management
  • Modular "per rack" architecture: Each rack is a self-contained unit — easy to add, move, or upgrade one rack without affecting others
  • Future-ready: Short copper allows transition to lower-power, higher-speed server I/O; ready for Unified Fabric (FCoE)
  • Easier troubleshooting: Problems are isolated to one rack's worth of servers
  • Easy per-rack speed migration: Upgrade one rack from 1G to 10G without touching others

❌ Why NOT ToR?

  • More switches to manage: One switch per rack → hundreds of switches in a large DC
  • Potential interoperability issues: Different vendors per rack
  • Higher switch costs and power: Hundreds of switches, each with power supply, cooling, management
  • Switch port utilization: If a rack isn't full, the ToR switch ports are wasted
  • More ports in aggregation: Each ToR needs uplinks to aggregation — aggregation switch needs more ports
  • STP complexity: More switches = more STP (Spanning Tree Protocol) instances to manage and tune
  • Layer 2 scaling issues: More Layer 2 server-to-server traffic at the aggregation layer; racks connected at Layer 2
  • Not enough density for high-density 1G environments
⚖️
Physical Structure

EoR — Pros and Cons

✅ Why EoR?

  • Fewer switches to manage: One switch per row instead of one per rack — far fewer devices
  • Lower switch and maintenance costs: Fewer higher-density switches
  • Fewer aggregation ports needed: One EoR switch provides one uplink instead of one per rack
  • Racks connected at Layer 1: Servers connect via direct copper patch cables — the switch boundary is at Layer 2 (the EoR switch). Fewer STP instances (per row, not per rack).
  • Accommodates 10G + high density 1G together: A single EoR switch can serve mixed-speed environments across the row

❌ Why NOT EoR?

  • Expensive, bulky copper cabling: Long copper runs (10–30m) from servers at far end of row to the EoR switch are heavy, rigid, and expensive
  • Cable management nightmare: Hundreds of long cables per row create dense, difficult-to-manage cable bundles
  • More patching infrastructure: Patch panels, cable trays, cable management arms all required
  • Limits high-speed I/O adoption: Long twisted-pair copper cables cannot support lower-power, higher-speed interfaces (e.g., 25G, 100G) that require short cables
  • High density of connections in EoR rack: Many cables converge on one rack
🔌
Physical Structure

Fabric Extender — The Hybrid Approach

A Fabric Extender is like having a "dummy outlet strip" at the top of each rack that connects via a single cable back to the intelligent power controller at the end of the row. All the intelligence lives in the controller; the outlet strips in each rack just forward everything upstream. From the controller's perspective, it owns all the ports in every rack — but physically, the outlet strips are distributed per rack.

The Fabric Extender (FEX) is a port multiplier, not a full switch. It sits at the top of each rack and connects to a central Controlling Bridge via fiber optic links. All switching intelligence resides in the controlling bridge.

Physical Structure

How to Connect Different Racks — The Aggregation Switch

Once servers within a rack are connected to a ToR switch, how do racks talk to each other? The standard answer: Aggregation switches connect multiple ToR switches and provide uplinks to a core switch or router.

Servers in Rack → ToR Switch (short copper) → Aggregation Switch (fiber uplink) → Core Switch/Router → Internet / Other DCs

This creates a 3-tier hierarchy: Access (ToR) → Aggregation → Core. This is the traditional enterprise network model applied to data centers.

⚠️
Physical Structure

The Traditional Model's Problem — Very Expensive N²

The traditional 3-tier model is like a city where all traffic must pass through the city hall (core switch) to get anywhere. As the city grows, city hall gets overwhelmed. You add a bigger city hall, then a bigger one — but it's always one bottleneck, always gets expensive, always reaches a limit.

Google's Jupiter Rising paper (SIGCOMM 2015) describes the traditional architecture problem with a real example (512 racks × 40 servers = ~20,480 servers):

  • 40 servers per rack × 1G each → 40G of server capacity per rack
  • Each ToR has only 4 × 1G uplink ports to the aggregation — so ToR can only deliver 4G upward out of 40G possible = 10:1 oversubscription ratio
  • Cluster routers have 512 × 1G downlinks (to ToRs) and only 2 × 10G uplinks to the core crossbar
  • The cluster router bottleneck: 512G in, 20G out = 25:1 oversubscription at the core

As data centers grew larger, aggregation switches ran out of ports, forcing the use of massive, expensive "big crossbar" switches — similar to ISP-grade IP routers — to interconnect multiple clusters. Problems with this approach:

  • Very expensive: Large crossbar switches cost millions of dollars each
  • Most capacity is "preparatory" (provisioned but unused): Built for peak load that rarely occurs
  • Difficult to configure and manage: Complex routing protocols, complex access control
  • Not scalable: Adding more racks means buying bigger switches — which eventually can't be built big enough, or cost prohibitively
  • Bandwidth bottleneck at the top: ToR switch has 1/10 the aggregate speed of all rack servers — traffic must stay mostly local to avoid congestion
The N² problem: Each aggregation switch connects N ToR switches. If every server wants to talk to every other server, the switch needs N × bandwidth. As N grows, cost grows roughly as N². Traditional large "big crossbar" switches follow this N² cost curve — they become impossibly expensive at cloud scale.
🌲
Physical Structure

Tree Network — An Alternative but Still Flawed

A tree network is like a company org chart — everything flows up through managers and VPs to the CEO. You can add more employees (leaves), but all decisions still flow through the top. The more employees you add, the more congested the top becomes — and if the CEO (root switch) fails, the whole company grinds to a halt.

Instead of one big crossbar switch, use a tree topology — multiple levels of switches organized like a tree. More racks can be added at the leaves, and the tree grows by adding more branches.

However, tree networks still have serious problems:

  • Reduced capacity as you go up: You can add more racks at the bottom, but the uplinks toward the root don't scale proportionally — traffic crossing pods must traverse the oversubscribed root links
  • Congestion at the top of the tree: All inter-pod traffic converges on root switches. With increasing machine-to-machine traffic (scatter-gather), root switches become bottlenecks.
  • Failure can partition the network: If a root or aggregation switch fails, it splits the network — servers in different parts of the tree can no longer communicate. No built-in redundancy at the top.
The fundamental issue with both traditional and tree topologies: They have a single path between any two servers that are not in the same rack. If that path is congested or fails, there's no alternative. Modern data center networks need multiple equal-cost paths and no single point of congestion or failure.
🕸️
Physical Structure

Clos Networks — The Modern Solution (Fat-Tree)

A Clos network is like a perfectly designed highway interchange — from any on-ramp, there are multiple alternative routes to any destination. No single road gets congested because traffic spreads across all available paths. And if one road closes, you just take another one. The total cost is also lower because you use many small, cheap switches instead of one giant expensive switch.

Clos networks (invented by Charles Clos in 1953 for telephone switching) are multi-stage switching fabrics that provide multiple parallel paths between any input and any output. Applied to data centers (the "fat-tree" variant), they create a 3-tier architecture:

TierNameRole
BottomServer / Access TierActual servers. Connected via ToR switches at the edge of the Clos fabric.
MiddleAggregation TierAggregation switches. Each aggregation switch connects to every server rack ToR in its "pod" AND to every core switch above.
TopCore TierCore switches. Each core switch connects to one aggregation switch in every pod — providing any-to-any cross-pod connectivity.

How Routing Works in a Clos Network

From the slide diagram (4 pods, servers labeled with IPs like 10.0.1.2, 10.2.0.2, etc.):

  • Each pod has its own set of aggregation switches connecting to its ToR switches (server access)
  • Core switches sit above all pods — each core switch connects to exactly one aggregation switch per pod
  • Multiple colored paths in the diagram show that traffic from Pod 0 to Pod 2 can take several different routes through different core switches — equal-cost multipath (ECMP)
Why Clos networks solve all three problems:
✅ No bottleneck: Any-to-any communication has multiple equal-capacity paths. Traffic spreads across all paths (load balancing).
✅ No single point of failure: Core switch failure? Traffic reroutes through other core switches automatically.
✅ Cost-effective: Uses many small, cheap commodity switches instead of one expensive behemoth. Each switch only needs to be large enough for its local connections — not for the entire fabric. Cost scales linearly, not quadratically.

Key Properties of Clos Networks

  • Connects any number of inputs to any number of outputs — fully non-blocking when properly sized
  • Consists of small-size switches — commodity merchant silicon switches (cheaper, more reliable, replaceable)
  • Bisection bandwidth can be made equal to total server bandwidth — full bisection bandwidth means no oversubscription
  • Multiple equal-cost paths allow load balancing — ECMP spreads flows across all available paths
  • Google's "Jupiter" network (described in the Jupiter Rising paper) is a real-world Clos fabric that scaled to support petabits of bandwidth using this approach
Clos vs. Traditional: In a traditional 3-tier with one core switch — that switch costs $1M+, is hard to scale, and is a single point of failure. In a Clos with 16 core switches — each costs $50K, together cost $800K, provide 16× the bandwidth, and losing one doesn't affect anything. This is why every major cloud provider (Google, Facebook, Amazon, Microsoft) uses Clos-based architectures.

North-South vs. East-West Traffic

In a traditional office, most email traffic went to customers outside the building (North-South — in and out the front door). In a modern cloud data center, servers mostly email each other internally (East-West — side to side). The network must be built for lateral communication, not just for traffic going in and out of the building.
DirectionDefinitionExampleVolume in cloud DC
North-SouthTraffic entering or leaving the data center — between users and the data center, or between the data center and the internet/other DCsUser's browser request arriving at a web server; web server sending a response back to the userSmall (~20% per Facebook data)
East-WestTraffic between servers within the data center — server-to-server communicationWeb server querying database; scatter-gather fan-out to 100 index servers; VM migration between physical hostsDominant (~80% per Facebook data)

The slide diagram shows a core switch at top with north-south traffic going upward (to internet) and downward arrows to ToR switches being east-west traffic flowing between server racks through the core switch. Also visible: east-west traffic within a single rack (server-to-server within the same ToR domain).

Design implication: Traditional enterprise networks were optimized for north-south traffic (client-server model). Cloud data center networks must be fundamentally re-architected to support massive east-west traffic. This means: high bandwidth between every pair of racks, not just between racks and the internet gateway. Clos networks provide exactly this property — full bisection bandwidth between any pair of servers regardless of location.

Exam Q&A — Test Yourself

🧪 Cloud Networking Exam Questions
Q1: What is the scatter-gather traffic pattern and why does it dominate cloud data center traffic?
A: Scatter-gather is the pattern where one request is fanned out (scattered) to many servers simultaneously, each processes a portion, then all send results back to the originator (gathered). It dominates because cloud applications like web search, recommendation engines, and distributed computing all work this way — breaking a large task into parallel sub-tasks processed by hundreds of servers. It generates enormous internal (east-west) traffic since every user request triggers many server-to-server messages internally.
Q2: What percentage of Facebook data center traffic stays within one data center vs. goes between data centers?
A: 82.3% stays within one data center (12.9% rack + 57.5% cluster + 11.9% DC-level). Only 17.7% is inter-DC. The largest single bucket is cluster-level at 57.5%, meaning most traffic stays within the same cluster of servers.
Q3: Explain the "tight deadline for network I/O" problem with the 100-server example.
A: In scatter-gather, the total response time equals the slowest individual server's response. If each server independently has a 1% chance of being slow (≥1 second), with 1 server: 1% of queries are slow. With 100 servers: probability that at least one is slow = 1 - (0.99)^100 ≈ 63%. So 63% of all queries are slow — what was a minor problem per-server becomes a majority problem for the aggregate. This is called tail latency amplification, and it's why network latency consistency (not just average latency) is critical.
Q4: What is TCP incast and how does it relate to data center traffic patterns?
A: TCP incast occurs when many servers simultaneously respond to the same receiver — a natural result of the scatter-gather "gather" phase. All those simultaneous flows converge on the same switch port and its buffer. If the buffer overflows, packets are dropped, TCP detects loss, goes into timeout/slow-start, which creates a cascading performance collapse. This is a direct consequence of scatter-gather workloads and is one of the key networking challenges the lecture identifies.
Q5: What is the difference between ToR and EoR physical layouts? When would you choose each?
A: ToR (Top of Rack) places a switch at the top of each individual rack — servers connect via short copper cables. EoR (End of Row) places a switch at the end of the entire row — all servers run long copper cables to it. Choose ToR when: you want cleaner cable management, modular per-rack architecture, better support for east-west traffic, easier speed upgrades per rack, and are ready for Unified Fabric. Choose EoR when: you want fewer switches to manage, lower switch costs, fewer aggregation ports, and can tolerate the large copper cabling infrastructure and cable management complexity.
Q6: What is a Fabric Extender and how does it differ from a regular switch?
A: A Fabric Extender (FEX) is a dumb port multiplier — it has no control plane of its own. It sits at the top of a rack, provides copper ports to servers, and connects via fiber to a Controlling Bridge switch. All intelligence (routing decisions, VLAN configuration, STP, ACLs) resides in the controlling bridge. From the network's view, all FEX ports appear to be directly on the controlling bridge. A regular switch has its own control plane and makes independent forwarding decisions. FEX combines ToR benefits (short copper, modular) with EoR benefits (fewer managed switches, fewer STP instances).
Q7: Why is the traditional 3-tier (aggregation with big core switch) model described as "Very expensive N²"?
A: In the traditional model, as more racks are added, the core switch must handle all cross-rack traffic. The bandwidth requirement at the core grows proportionally to N (number of racks) squared because every rack potentially communicates with every other rack. A switch capable of handling N² connections becomes exponentially more expensive as N grows — commercial implementations of these "big crossbar" switches cost millions of dollars, are difficult to configure, and eventually hit physical port density limits. This makes the traditional model fundamentally unscalable for cloud-scale data centers.
Q8: What are the three problems with tree networks?
A: (1) Reduced capacity at higher levels: Adding racks at the bottom doesn't add proportional bandwidth at the top — links toward the root are oversubscribed, especially with increasing machine-to-machine (east-west) traffic. (2) Congestion at the root: All inter-pod traffic must traverse root switches, making them bottlenecks when scatter-gather traffic creates heavy cross-pod communication bursts. (3) Failure can partition the network: Root or upper-level switch failure splits the tree, disconnecting groups of servers from each other — no built-in redundancy at the top levels.
Q9: Explain how a Clos (fat-tree) network solves the problems of traditional topologies.
A: A Clos network has three tiers: server access → aggregation (per pod) → multiple core switches. Each aggregation switch connects to all ToRs in its pod AND to all core switches. Each core switch connects to one aggregation switch in every pod. This creates multiple equal-cost paths between any pair of servers. It solves: (1) bottleneck — traffic distributes across all core switches via ECMP, so no single switch is overloaded; (2) failure resilience — losing one core switch just reduces total bandwidth, other paths continue; (3) cost — uses many small commodity switches instead of one giant expensive switch; cost scales linearly with the number of racks.
Q10: What is the difference between North-South and East-West traffic in a cloud data center?
A: North-South traffic flows between the data center and the outside world — user requests coming in, responses going out. East-West traffic flows between servers within the data center — machine-to-machine communication. In cloud data centers, east-west dominates (82.3% internal per Facebook data, 76% per Cisco). Traditional enterprise networks were optimized for north-south; cloud data centers require network redesign to support massive east-west bandwidth between any pair of servers, which is why Clos architectures were adopted.
Q11: Why is centralized control at the flow level difficult in large data centers?
A: Facebook data shows flow inter-arrival times of approximately 2ms — new connections are established every 2ms per server, multiplied across thousands of servers. For a central controller to manage each flow, it would need to: receive a notification about the new flow, make a routing decision, and program the network switch — all within 2ms. The round-trip latency to a central controller plus processing time is often longer than the flow's entire lifetime. Additionally, at millions of flows per second across the whole data center, a centralized controller would be overwhelmed computationally. SDN can help at the policy/aggregate level but per-flow centralized control is impractical.
Q12: What is the impact of server virtualization on data center networking?
A: Server virtualization multiplies the number of network endpoints dramatically — one physical server with 10 VMs appears as 10 separate network devices, each with its own MAC address, IP address, and network flows. This: (1) increases the total number of network flows the fabric must handle; (2) creates the need for network isolation between VMs from different tenants sharing the same physical server; (3) requires the network to support VM migration — when a VM moves from one physical server to another, its network identity must move with it (live migration). The Cisco Cloud Index predicted this would have a large impact on cloud data center network design.
